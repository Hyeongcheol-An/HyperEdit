# HyperEdit 설계와 결정 이력

> HyperEdit가 왜 이런 모양인지, 무엇을 어떤 이유로 결정했는지, 그 과정에서 배운 기술적 사실은 무엇인지 기록하는 문서입니다. 사용법은 [README.ko.md](../README.ko.md), 기능 목록과 상태는 [features.md](features.md), 폰트는 [fonts.md](fonts.md), Zed 테마는 [zed.md](zed.md)를 보세요.

## 1. 한 문장 요약

**계속 길어지는 메모 파일 하나(수만 줄)를 끝에 덧붙이고 검색하는 습관을 그대로 살리면서, 고전 리본 에디터의 편집 도구(열 모드·북마크·검색 결과 창·텍스트 도구)와 현대 에디터의 가벼움을 macOS 네이티브로 구현한다.**

| 항목 | 현재 |
|---|---|
| 플랫폼 | macOS 15+ (유니버설). 엔진은 iOS 18 타깃도 선언하지만 iOS 앱은 아직 없음 |
| 스택 | Swift 6 툴체인 · Swift 5 언어 모드 · SwiftUI 셸 + AppKit `NSTextView`(TextKit 2) · 공유 패키지 `HyperCore` |
| 데이터 | 로컬 일반 텍스트 파일(UTF-8·EUC-KR·CP1252·Latin-1 무손실 판별). 파생 데이터는 Application Support 아래의 북마크 JSON·스냅샷 사본·스니펫(`snippets.json`)·매크로(`macros/macros.json`) JSON 뿐 |
| 동기화 | 없음(로컬 전용). iCloud 연동은 보류 (§7) |
| 테마 | 22종, `themes/palettes.json` 단일 소스 → 앱 테마 + Zed 테마. 이름은 모두 `Hyper ` 접두사, 기본값은 시스템 외형을 따르는 **Hyper Light / Hyper Dark** |
| UI | 고전 UltraEdit 리본 레이아웃에서 영감(리본 탭·그룹, 문서 탭, 사이드바, 하단 패널, 상태바). UltraEdit는 IDM Computer Solutions의 상표이며 HyperEdit는 무관한 독립 프로젝트 |
| 배포 | GitHub Releases DMG(Developer ID 서명·공증) + Homebrew tap. MIT 라이선스 |

## 2. 문제 정의

- 대상 문서는 "한 파일에 계속 append" 하는 메모다. 수만 줄, 1 MB 이상, 코드·로그·한글 메모·URL이 섞여 있고 마크다운 구조는 거의 없다. `#`으로 시작하는 줄은 헤딩보다 파이썬 주석일 때가 더 많다.
- 그런 파일에서 필요한 것은 ① 키 입력 지연이 없는 편집, ② 즉시 응답하는 검색과 결과 목록, ③ 구조 없는 텍스트에 사후적으로 구조를 부여하는 탐색(아웃라인·타임라인·북마크), ④ 표 형태 텍스트를 다루는 열 모드와 줄 단위 텍스트 도구다.
- 기존 도구는 각각 일부만 충족했다. 범용 코드 에디터는 가볍지만 북마크 패널·열 모드 숫자 채우기 같은 도구가 없고, 리본 에디터는 도구는 풍부하지만 macOS 네이티브가 아니거나 큰 파일에서 무겁다.

### 4.1 상태 흐름

- `AppModel`(메인 액터)이 UI 상태와 명령을 들고, 편집기에는 `PassthroughSubject<EditorCommand>`로 명령을 보낸다. 문서 상태(`MemoDocument`)는 AppModel을 거치지 않고 필요한 뷰가 직접 `@ObservedObject`로 구독한다.
- 키 입력마다 바뀌는 캐럿 정보는 `EditorCaret`라는 별도 객체로 발행한다. 상태바·아웃라인·타임라인만 구독하고 리본·패널은 다시 그려지지 않는다.
- 무거운 작업(검색, 줄 인덱스 재계산, 아웃라인 스캔, 파일 쓰기)은 텍스트의 불변 사본을 들고 `Task.detached`에서 돌린 뒤 결과만 메인 액터로 돌아온다.

### 4.2 문서와 저장

- `MemoDocument`가 `NSTextStorage`를 직접 소유해 텍스트 뷰와 공유한다(MB 단위 문자열 복사 회피).
- 저장: 입력이 멈추고 2초 뒤 자동 저장. 모든 디스크 쓰기는 하나의 직렬 큐를 지나며, 종료(`applicationShouldTerminate`)·창 닫기·파일 전환 시에는 `saveSynchronously()`로 같은 큐에서 동기 저장하므로 2초 창에서의 손실이 없다. 불변 사본을 원자적으로 쓴다. 세션 첫 저장 전 `~/Library/Application Support/HyperEdit/snapshots/<파일명>-<시각>-before-first-save.txt` 사본을 남기고, 스냅샷을 만들 때마다 파일별 최신 20개·90일 보관 정책으로 정리한다. 빈 버퍼를 내용이 있던 파일 위에 쓰려 하면 차단하고 상태바에 알린다.
- 인코딩: UTF-8(BOM은 떼어 기억) → EUC-KR(CP949) → CP1252 → Latin-1 순으로 **손실 없이** 디코딩되는 것을 고르고 저장도 같은 인코딩으로 한다. 원 인코딩에 없는 문자(예: EUC-KR 파일의 이모지)가 생기면 UTF-8로 변환 저장하고 상태바에 알린다. 어느 인코딩으로도 읽을 수 없는 데이터는 열지 않는다 — 손실 디코딩 뒤 자동 저장하면 파일이 망가지기 때문이다.
- 외부 변경: `DispatchSource`로 파일을 감시한다. 자기 쓰기 직후 1.5초는 무시하고, 다른 앱의 원자적 저장(삭제/이름 변경 이벤트)은 잠시 뒤 새 inode를 다시 감시한다. 버퍼가 깨끗하면 재로드하되 직전 캐럿 위치(클램프)를 복원해 읽던 자리를 잃지 않는다. 수정 중이면 외부본을 `-external` 스냅샷으로 보관하고 경고한다.
- 파일 전환: 새 `MemoDocument`를 만들지 않고 `switchTo(url:)`로 같은 객체·같은 `NSTextStorage`의 내용만 바꾼다(§5 성능 메모 2). 전환 직전 dirty면 동기 저장하고, 전환 전 시작된 저장 콜백은 `fileGeneration` 세대 가드로 무시한다.
- 북마크: `BookmarkStore`가 문서 경로의 SHA-256 해시를 이름으로 `~/Library/Application Support/HyperEdit/bookmarks/<해시>.json`에 저장한다. 문서 폴더에 숨김 파일을 만들지 않고 읽기 전용 볼륨의 파일도 북마크할 수 있다. 예전 버전이 문서 옆에 만들던 `.<파일명>.bookmarks.json` 사이드카는 읽기만 해서 1회 이전하고, 쓰지도 지우지도 않는다.

### 4.3 편집기

- `HyperTextView`는 TextKit 2 `NSTextView` 서브클래스. 멀티 커서와 열 블록은 추가 선택 범위 배열로 들고 있고, 모든 멀티 편집은 `shouldChangeText(inRanges:)` → `replaceCharacters` → `didChangeText` 경로를 타므로 ⌘Z 한 번으로 되돌려진다.
- 열 블록 수학(`ColumnBlock`)은 문자 열(UTF-16 오프셋) 기준이다. 줄이 짧으면 가상 공백으로 간주해 삽입 시 공백으로 채운다. 블록 안에서만 편집이 일어나므로 최상단 줄 시작 오프셋은 편집 중 변하지 않는다.
- 줄 번호 거터는 `NSRulerView`가 아니라 독립 `NSView`(`GutterView`)다(§5 기술 메모).
- 검색 결과가 있으면 매치 범위에 배경색 속성만 얹어 편집기 안에서 강조한다(최대 3,000개). 저장되는 문자열과 undo 스택에는 영향이 없다.
- 아웃라인·타임라인은 줄 인덱스가 바뀌고 1.2초 뒤 백그라운드에서 다시 스캔한다. 아웃라인은 `#` 헤딩·`[제목]`·`가./나.`·`1)`를 뽑되, 마크다운이 아닌 파일에서 코드 주석처럼 보이는 1단계 `#` 줄은 제외하고, 타임스탬프 헤딩은 타임라인으로 보낸다. 타임라인은 정확한 타임스탬프 헤딩과 날짜로 시작하는 느슨한 줄(연속 로그는 첫 줄만)을 모은다.

### 4.4 테마 엔진

- `themes/palettes.json`의 각 항목은 배경·전경·강조·선택·ANSI 16색·구문 색 등 소수의 필수 색만 가진다. `build_zed_theme.py`가 거기서 Zed 테마 스키마의 모든 스타일 키와 구문 키를 유도하고, Swift 쪽 `Theme`도 같은 JSON(패키지 리소스로 복사)을 읽는다.
- `build_preview.py`는 22개 카드가 들어간 `docs/theme-preview.html`을 만든다(외부 리소스·JS 없음). `validate.py`는 생성된 Zed 테마가 스키마 키를 모두 갖추고 색 형식이 맞는지 검사한다.
- CI는 생성물을 다시 만들어 커밋본과 비교한다. 팔레트를 고치고 생성물을 커밋하지 않으면 실패한다.
- `ThemeStore`: 저장된 선택이 없으면 시스템 외형 따르기(라이트 → `hyper-light`, 다크 → `hyper-dark`). 직접 고르면 고정되고, 레이아웃 탭·상태바·보기 메뉴의 테마 메뉴와 설정에서 다시 켤 수 있다(따르는 중이면 테마 이름 옆에 "· 시스템"). 앱은 `NSApplication.effectiveAppearance`를 구독해 시스템 전환을 전달한다.

### 4.5 폰트

- 본문 폰트는 Fira Code(없으면 시스템 고정폭), 캐스케이드에 한글 폰트를 끼운다. 한글 런에는 `HangulFontFixer`가 한글 폰트 ×1.2 크기를 속성으로 직접 입힌다. 줄 높이는 본문 폰트 기준으로 고정해 한글 폰트가 커도 줄 간격이 들쭉날쭉하지 않다. 근거와 대안은 [fonts.md](fonts.md).

## 5. 기술 메모 (실측·실수에서 배운 것)

### TextKit 2
- **`NSRulerView`를 TextKit 2 `NSTextView`에 붙이면 본문이 그려지지 않는다**(macOS 15 SDK 이후 실측). 줄 번호 거터는 스크롤 뷰 왼쪽에 독립 `NSView`로 두고 클립 뷰 bounds 변경에 맞춰 다시 그린다.
- TextKit 2 본문은 GPU 서피스로 합성되어 `cacheDisplay(in:to:)`로는 캡처되지 않는다. 화면 검증(`--snapshot`)은 **ScreenCaptureKit**으로 실제 창을 캡처한다(화면 녹화 권한 필요).
- 선택이 바뀔 때 전체 `needsDisplay`를 켜면 서피스 재합성이 일어난다. 현재 줄 강조는 이전·현재 줄 두 영역만 무효화한다.
- `NSTextContentStorage.textStorage`를 파일마다 갈아끼우면 TextKit 2 레이아웃 질의(`endEditing`·`scrollRangeToVisible`·거터 그리기)가 전환을 반복할수록 2 KB 문서에서도 50 ms대로 퇴화한다. 문서 객체와 스토리지를 유지한 채 전체 범위 `replaceCharacters`로 내용만 바꾸면 정상 편집 경로라 수 ms다.
- **배치 전·그리는 중의 레이아웃 질의는 조각 프레임을 옮긴다**(macOS 27 실측, 실사용 하네스 2026-11-24). `enumerateTextLayoutFragments(.ensuresLayout)`·`textLayoutFragment(for: CGPoint)`·`caretRect` 가 뷰포트 위의 아직 배치하지 않은 문단을 배치하면 그 아래 조각들의 프레임이 통째로 옮겨지는데, 이미 화면에 올린 조각 뷰는 다시 놓이지 않는다 — 글자는 옛 자리에 보이고 줄 번호·접기 표식·클릭 판정은 새 자리를 따른다(모두 접기 뒤 9~36 pt). 그리기 경로는 질의 앞뒤로 뷰포트 마지막 조각의 y 를 견줘 움직였으면 다음 턴에 `needsLayout` 을 건다(`HyperTextView.guardingViewport`). 스크롤 직후의 첫 줄 질의(`publishFirstVisibleLine`)는 밀린 배치를 먼저 끝낸다 — 그러지 않으면 쉬었다가 위로 굴리는 첫 걸음이 20~100 pt 덜 가거나 거꾸로 간다.
- **스크롤이 일어나지 않은 `scrollRangeToVisible` 뒤에는 `viewportRange` 가 빈 범위다**(방향키로 캐럿만 옮긴 경우). 보이는 범위를 그 값으로 정하던 검색 강조가 다시 그려지는 줄마다 지워졌다 — 배치된 조각을 직접 세고(`laidOutCharacterRange`), 범위가 비면 뷰포트를 한 번 더 배치한다.
- **끝으로 점프하면 스크롤 위치가 줄어든 문서 높이를 넘긴 채 남는다**(`layout()` 한 번 안에서 문서 높이가 +93,412 → −48 로 바뀌고 위치 보정은 되돌려진다). 마지막 줄 아래에 60~306 pt 의 빈 띠가 생기고 다음 휠에서 그만큼 튄다 — 배치 뒤와 `scrollRangeToVisible` 뒤에 클립 뷰가 허용하는 범위로 되돌린다(`constrainScrollToDocumentEnd`; 트랙패드 제스처 중에는 탄성을 살리려고 건드리지 않고 제스처가 끝난 알림에서 한 번 본다 — 제스처인지는 시작 알림에서만 가린다, 아래 '반응형 스크롤').
- **문서 좌표로 스크롤을 검증하면 안 된다.** TextKit 2 는 스크롤할 때마다 추정 높이를 실측으로 바꾸며 `visibleRect.minY` 와 문서 높이를 수십 pt 씩 다시 잡는다. 화면에서의 이동은 닻 문단의 화면 y 로 잰다(실사용 하네스의 `checkContentMoved`).
- **거터·상태바의 줄 번호는 편집마다 증분 갱신되는 줄 인덱스로**(`MemoDocument.liveLineIndex`). 입력이 멈춘 250 ms 뒤에 다시 세는 발행용 `lineIndex` 로 그리면 Enter·줄 합치기 뒤 치는 동안 내내 번호가 한 줄 어긋난다.
- **거터 폭은 그릴 때가 아니라 편집할 때 정한다.** 줄 수의 자릿수가 바뀐 것을 그리는 중에야 알면(`GutterView.drawImpl` → `updateThickness`) 컨테이너의 배치가 한 패스 늦는다. 보이는 창은 다음 프레임이 그 패스를 돌리지만, 완전히 가려진 창에는 제 디스플레이 주기가 없어 누가 배치를 시킬 때까지 거터의 틀이 옛 폭으로 남는다(10,000 → 9,999줄에서 폭 62 pt, 틀 69 pt — 창이 가려진 실행에서 두 번 중 두 번, 보이는 실행에서는 0번). `textDidChange` 에서, 분할의 다른 편집기는 편집이 전해질 때(`EditorSession.didEdit`) 폭을 맞춘다 — 편집 뒤의 배치 패스가 이미 새 폭을 쓴다.
- 접을 때 선택이 숨은 줄에 남으면 그 상태로 친 글자가 보이지 않는 선택을 지운다 — 통째로 숨는 선택은 머리 줄 끝 캐럿으로, 한쪽만 숨으면 보이는 자리까지 당긴다(`FoldController`). 여러 캐럿·열 블록도 캐럿마다 같은 규칙으로 옮긴다(숨은 캐럿은 머리 줄 끝으로, 겹치면 하나로; 보이는 캐럿은 그대로): 네이티브 선택(머리 캐럿)만 보면 나머지가 새 접힘 안에 그려지지 않은 채 남아 다음 키가 숨은 줄을 고쳤다. 열 블록은 줄을 건너뛸 수 없으므로 행이 하나라도 숨으면 머리 캐럿 하나로 접는다. 순서도 중요하다 — 네이티브 선택을 먼저 건드리면 그 선택 통지가 올 때 여러 캐럿의 범위가 아직 옛 값이라 선택 변경 감시가 방금 접은 것을 도로 편다(머리 캐럿이 숨는 쪽이면 접기 명령이 아무 일도 하지 않았다). 여러 캐럿을 다시 놓을 때 화면은 **머리 캐럿이 숨어서 옮겨졌을 때만** 따라간다(`setMulti(reveal:)`): 머리 캐럿은 문서 순서로 마지막 캐럿이라, 모든 일치를 고른 채 문서 위쪽의 구역을 접자 화면이 마지막 일치로 가 버리고 방금 접은 자리가 화면을 떠났다(맨 위 줄 69 → 469). 모두 접기를 캐럿이 화면 밖에 있을 때 하면 캐럿을 따라가지 않고 읽던 곳에 남는다 — 캐럿이 하나일 때도 같다(전에는 캐럿의 머리 줄로 뛰었다). **"머리 줄 끝"은 숨김 구간 시작 − 1 이 아니라 그 줄의 내용 끝이다**(`FoldStore.headerEnd(before:)`): 줄이 CR LF 로 끝나면 시작 − 1 은 `\r` 과 `\n` 사이라, 접은 뒤 거기 놓인 캐럿에 친 글자가 줄 끝을 깨뜨렸다(`):\rQ\n` — 혼자인 CR 과 혼자인 LF 가 생기고 아래 거터 번호가 한 줄 어긋난다). 캐럿·접힘 밖으로 옮긴 캐럿(하나든 여럿이든)·모두 접기의 닻·표식이 그 자리를 쓰고, 접힘을 건너는 ↑/↓ 도 `\r` 앞에 멈추며, 글자 한 걸음은 CR LF 를 한 걸음으로 센다. LF 로만 끝나는 줄에서는 모든 값이 전과 같다. 혼자인 `\r` 줄 끝(옛 Mac 형식)은 다루지 않는다.
- **레이아웃 관리자는 배치한 조각을 2,000개까지만 붙든다**(비공개 `maximumNumberOfCachedTextLayoutFragments`). 넘으면 뷰포트 배치 때 뷰포트 밖 조각을 전부 버리고, 버려진 문단의 높이는 추정값으로 돌아간다 — 그 추정이 실제의 157 %(Fira Code 에서 줄당 글자 수를 절반으로 어림)라 2,000 문단쯤 훑은 걸음에 화면이 수백 줄 튄다. 조각 표는 문단을 약한 참조로 든 `NSMapTable` 이라 문서를 통째로 바꾸면(탭 전환·다시 읽기·전체 속성 적용) 죽은 항목이 항목 수에 남고, 그것이 상한을 넘기면 **모든** 배치 패스가 조각을 버린다 — 앱을 다시 띄울 때까지 어느 문서에서나 휠 75 pt 에 화면이 0.3 / 51 / −46 pt 움직인다. 대응은 둘이다: (1) **스크롤 닻**(공개 API) — 배치 패스가 끝날 때 뷰포트 맨 위·맨 아래 조각의 자리를 적어 두고, 편집·보이게 스크롤·리플로가 아닌 다음 패스가 그 조각을 화면에서 옮겼으면 그만큼 스크롤을 되돌린다. (2) 조각을 버린 패스 뒤에 상한을 "남은 항목 수 + 2,000" 으로 다시 잡는다(비공개 값 — 있을 때만). 상한을 아예 없애면 입력이 조각당 약 5 µs/키 느려진다(문서 전체 배치 시 8.9 → 129 ms/키). **남은 결함**: 한 화면(382 pt)을 넘는 걸음(800 pt 휠)이 조각을 버리는 걸음과 겹치면 걸음 앞뒤로 화면에 남는 조각이 없어 스크롤 닻이 어림으로만 바로잡는다 — 내용이 22~61줄 거꾸로 간다(실사용 하네스 `scroll-knob` 이 걸음을 적는다).
- **글꼴의 leading 은 고정 줄 높이 위에 더해진다**(`NSTextLayoutManager.usesFontLeading` 기본 true). 한글 글꼴(D2Coding) 줄만 25.34 pt 가 돼, 맨 아랫줄에서 한글을 조합하면 줄이 자라 AppKit 이 화면을 가운데로 다시 맞췄다(219 pt). `usesFontLeading = false` 로 모든 줄이 24 pt.
- **화면 밖으로 나간 캐럿은 AppKit 이 가운데로 데려온다**(`scrollRangeToVisible` — 방향키 한 번에 반 화면). 캐럿을 한 줄·한 글자·한 단어 옮기는 명령에서는 캐럿 줄이 다 들어올 만큼만 직접 민다(`revealCaretStep`). 입력도 같다: `-[NSTextView _insertText:replacementRange:]` 가 편집 직후 `scrollRangeToVisible` 을 불러, 382 pt 화면의 맨 아랫줄에서 Enter 를 치면 213 pt, 글자를 쳐 줄이 감기면 192 pt 가 밀렸다 — `insertText`·`setMarkedText`(조합)·`insert…`/`delete…` 명령이 부른 것이면(`editRevealDepth`) 같은 함수로 넘은 만큼만 민다(Enter 한 번에 24 pt). AppKit 그대로인 것: Page Up/Down·문서 처음/끝으로·줄로 이동·찾기 점프·실행 취소, 캐럿이 한 화면 넘게 가거나 편집 시작에서 64 문단 넘게 떨어진 큰 편집, 화면 위에서 시작한 편집(다음 항목), 문서의 마지막 줄에서의 입력(문서가 자라는 중이라 텍스트 뷰의 높이가 아직 옛 값이다). **줄바꿈 끔에서도 같은 함수가 민다** — 꺼 두었을 때는 맨 아랫줄의 ↓·Enter·입력과 맨 윗줄의 ↑·Backspace 가 382 pt 화면에서 192 pt 씩 밀렸다. 이 함수는 세로만 옮기고 AppKit 의 '보이게 스크롤'을 부르지 않으므로, 줄바꿈 끔의 가로는 바로 이어서 맞춘다(`revealNoWrapColumn` — 캐럿, 선택을 늘리는 중이면 움직인 쪽 끝, 멀티 캐럿이면 머리 캐럿): 왼쪽 가장자리를 넘으면 넘은 만큼, 오른쪽이면 AppKit 이 하던 대로 보이는 폭의 가운데로. 오른쪽도 한 글자씩 밀면 긴 줄의 끝에서 치는 동안 키마다 화면 전체가 옆으로 밀려 다시 그려진다(긴 문단이 많은 문서에서 키당 14.1 → 17.5~18.2 ms). 편집이 선택을 남겼으면(스니펫의 자리표시자, 입력기의 절) 범위 전체가 보이는 열에 오게 끝을 보이고 이어서 시작을 보인다 — '움직인 쪽 끝'은 걸음 전의 선택과 견줘 고르는데 그 값은 방향키 명령만 적으므로, 편집 뒤에 견주면 낡은 값이라 한쪽 끝만 보이고 다른 쪽이 가장자리 밖에 남았다(선택 x 697…878, 보이는 x 0…757). 그리고 보이는 높이는 패스마다 다시 읽는다: 줄바꿈 끔에서는 이 함수 안의 뷰포트 배치가 화면보다 넓은 줄을 처음 만나 텍스트 뷰를 넓히면, 스크롤 막대를 항상 보이는 설정에서 가로 막대가 그때 생기며 화면이 낮아진다(382 → 365 pt — 처음 높이로 맞춘 캐럿 줄이 새 가로 막대 밑에 17 pt 잘렸다).
- **편집 직후의 캐럿 줄 자리는 추정이다.** 편집 직후 TextKit 2 는 고쳐진 문단의 높이를 추정값으로 되돌려 두므로 그 아래 조각의 자리(캐럿 사각형)가 다음 뷰포트 배치까지 어긋나 있다(한 줄 문단 끝에서 Enter — 새 줄의 캐럿이 24 pt 아래로 나와, 새 줄이 화면에 들어가는데도 넘은 것으로 보였다). 조각을 배치만 해서는(`.ensuresLayout` 열거) 아래 조각의 자리가 고쳐지지 않는다. `layoutViewport()` 한 번이면 정확하지만 Enter 마다 0.3 ms 남짓이라 한 턴에 되풀이하는 매크로에서 쌓인다 — 편집된 문단의 위 가장자리(그 위는 배치돼 있어 그대로다)에서부터 캐럿 문단까지의 실제 높이를 더한다(`caretLineAfterEdit`, 64 문단까지). 그보다 먼 편집을 뷰포트 배치로 재면 안 된다: 문서 전체가 바뀐 직후의 문서 끝에서는 그 배치가 문서를 처음부터 훑는다(아래 '문서 끝 너머'). 네 가지 단서가 붙는다. (1) 그 합은 편집된 문단이 **화면에 그려 둔 범위(뷰포트) 안에서 시작할 때만** 맞다(`editStartsOnScreen`). 화면 위의 한 번도 배치하지 않은 곳에서 시작한 편집 — 화면 밖에 있는 멀티 캐럿 — 은 시작 자리부터 어림이라 캐럿 줄이 실제보다 295~1,900 pt 위로 나왔고, 그 사이의 문단을 배치하는 것만으로 화면의 글이 밀렸다(글자 하나에 192 pt, 또는 1,047~2,052 pt — 편집 뒤의 패스라 스크롤 닻은 쉰다). 그런 편집은 재지 않고 AppKit 에 맡기며, 레이아웃 매니저에 조각을 묻지도 않는다(편집 트랜잭션 안에서는 읽기 열거도 좌표를 옮겼다). (2) 64 문단을 넘어 AppKit 에 맡긴 큰 붙여넣기: AppKit 은 그 사이 문단들의 추정 높이로 잡은 자리로 가므로, 뒤따르는 배치가 실측으로 바꾸면 캐럿이 화면 밖에 남을 수 있다(1.3 MB 메모의 가운데에 600줄을 붙여넣자 화면 아래 182 pt) → 다음 턴에 캐럿이 보이는지 한 번 더 본다(`revealCaretAfterRelayout`). (3) 문서를 통째로(절반 넘게) 바꾼 편집(`editRevealWholesale` — 문서 전체를 바꾸는 도구)은 (1)·(2)에서 뺀다: 화면의 배치가 남아 있지 않아 밀릴 글이 없고, 다음 턴에 다시 재면 그 배치가 문서 전체를 훑는다(전체 주석 토글 1.5~2.2 s). 다만 그때도 편집 시작의 64 문단은 배치해 둔다 — 배치된 조각이 하나도 없으면 높이 어림이 없어, AppKit 이 캐럿으로 데려간 자리가 문서 끝 너머가 되고 다음 패스가 문서를 처음부터 끝까지 배치한다(1.3 MB 에서 1.1 s). (4) 통째 편집은 문서 처음에서 시작하므로 그 64 문단은 아무도 보지 않는 문단이다 — 그런 편집에서는 재기 전에 길이를 먼저 훑어(문단 경계 탐색은 memchr 수준이다) 거대 문단(2만 자 초과)이 끼어 있으면 재지 않고 AppKit 에 맡긴다: 그 높이를 알려면 문단 전체를 배치해야 한다(26,000자 문단 하나에 26 ms; 첫 64줄이 그런 JSONL 파일의 끝을 보며 전체 주석 토글을 하자 0.5 s 가 2.1 s 가 됐다). 미리 배치는 거대 문단을 건너뛴 첫 보통 문단들로 한다(2,178 ms → 396 ms); 64개가 전부 거대 문단이면 아무것도 배치하지 않는데, 그래도 다음 패스가 문서를 훑지는 않았다(가라앉기까지 24~28 ms, 조각 표 +11~15). **화면에서 시작한 편집에는 이 건너뛰기를 하지 않는다**: 그 문단은 그리려고 어차피 배치하는 것이고, 건너뛰면 화면에 보이는 거대 문단 바로 뒤의 Enter 가 AppKit 의 가운데 맞춤으로 넘어간다(맨 아랫줄에 걸친 26,000자 줄 끝에서 Enter 한 번에 202 pt — 한 줄은 24 pt). 빈 문서에 큰 붙여넣기를 해도 문서 전체 배치는 나지 않는다(1.3 MB·24,000줄 194~220 ms, 조각 +16 — 한 줄 있던 문서에 붙여넣을 때와 같다; `typing-paste-empty` 가 지킨다).
- **한 턴 안에서 되풀이되는 편집(매크로 재생)은 걸음마다 따라가면 안 된다.** 재생은 런루프 한 턴 안에서 편집과 캐럿 이동을 되풀이하고 그 사이에 배치 패스가 없다 — 앞서 고친 문단들의 높이가 어림으로 돌아가 있어 캐럿 줄이 실제보다 아래로 재어진다(여덟 줄을 고친 뒤 +192 pt). 걸음마다 따라가면 그 자리로 화면을 밀고, 뷰포트를 배치하고, 다시 재서 되돌린다: 10단계 매크로 100회에 그런 왕복이 13~16번(뷰포트 배치 두 번씩), 방향키의 한 줄 밀기가 86번이었다. 재생 중에는 `scrollRangeToVisible` 이 아무것도 하지 않고(`isReplayingMacro`), 재생하는 쪽이 런루프에 양보하기 직전과 끝에서 한 번씩 뷰포트를 먼저 배치해 자리를 실측으로 바꾼 뒤 방향키와 같은 규칙으로 민다(`revealCaretAfterReplaySteps`; 한 화면 넘게 갔으면 AppKit 이 데려간다). 1.2 MB 문서에서 100회 재생 844~880 ms → 645~652 ms, 화면은 캐럿이 보이는 동안 움직이지 않는다.
- **리플로는 스크롤 좌표를 그대로 둔 채 모든 문단을 추정 높이로 되돌린다**(확대·테마·줄바꿈·줄 번호·폭 변화·파일 다시 읽기). 같은 y 에 다른 줄이 온다 — 바꾸기 전에 줄 하나를 잡아 두었다가(`captureReadingAnchor`: 캐럿이 화면에 있으면 캐럿 줄, 아니면 맨 위 줄; 문서 끝을 보고 있었으면 끝에 붙임) 실제로 배치된 뷰포트를 확인하며 같은 높이로 되돌린다(`restoreReadingAnchor`). 그 결과는 스크롤 닻의 새 기준으로 넘긴다 — 안 그러면 닻이 낡은 기록으로 되돌린다(줄 이동이 36.8 pt 어긋났다). 폭이 바뀐 뒤에는 옛 폭에서 잰 높이가 추정값으로 남으므로(`invalidateLayout(for:)` 로는 버려지지 않는다) 저장소에 속성 편집 통지를 보내 다시 재게 한다.
- **전체 무효화 직후의 점 질의는 화면의 조각 뷰는 그대로 두고 조각 프레임만 옮긴다**(실측 −102 pt). 보기 위치 저장·첫 줄 발행·거터는 그려 둔 뷰포트에서 답을 얻고(`laidOutViewport`), 쓸 수 없을 때만 지킴이(`guardingViewport`) 안에서 점 질의를 한다.
- **문서 끝 너머에서 부른 `layoutViewport()` 는 문서 전체를 훑는다.** 문서 전체의 레이아웃이 무효가 된 뒤(글자 크기·폭·줄바꿈·접기) 높이 어림이 줄면 스크롤 위치는 옛 높이의 것이라 새 문서의 끝을 넘어 있다. 그 자리에서 뷰포트를 배치하면 TextKit 2 는 그 높이의 문단을 찾지 못해 문서 처음부터 — 닿지 못하므로 끝까지 — 문단을 차례로 배치한다(문단마다 구문 색 렌더링 속성을 얹는 비용이 대부분이고, 끝난 뒤의 문서 높이는 전부 배치한 실제 높이다): 문서 끝에서 글자를 줄이거나 사이드바를 닫으면 1.3 MB 메모에서 그 한 번이 457~694 ms, 4 MB 로그에서 5 s. 높이가 늘어나는 변화는 같은 자리에서 5~7 ms 다. 읽기 닻을 되돌리는 첫 패스 앞에서 마지막 문단 하나만 배치해 끝의 자리를 묻고(1 ms), 스크롤 위치가 그 너머면 끝에서 세 화면 위로 먼저 옮긴다(`enterDocumentBeforeViewportLayout`) — 그 값과 TextKit 이 위치를 찾을 때 쓰는 높이 어림이 수백 pt 어긋날 수 있어(실측 ±560 pt) 끝에 바짝 붙이지 않고, 맞추기는 뒤따르는 닻 루프가 한다. 문서 끝의 1.3 MB 메모에서 글자 줄이기·사이드바 닫기·분할 닫기의 정지 0.47~0.81 s → 250 ms 넘는 정지 없음.
- **문서 전환도 같은 함정이다.** 탭 전환·파일 열기는 같은 저장소의 내용을 통째로 바꾸는데 스크롤 위치는 앞 문서의 것이라, 새 문서가 더 짧으면 문서 끝 너머다 — 보던 곳을 되살리기 전에 배치 패스가 한 번 돌면 TextKit 2 가 문서를 처음부터 끝까지 배치한다(24,000줄 문서의 끝을 보다가 12,002줄 JSON 을 열자 그 패스 한 번이 17.5 s: 문단마다 얹는 구문 색 렌더링 속성의 런 배열이 문단 수의 제곱으로 든다). 그 뒤로는 문서 전체에 렌더링 속성이 깔려 있어 큰 편집마다 맞춤법 검사기가 그것을 훑는다(JSON 정리 150 ms → 3.1 s — 셀프테스트의 `format JSON on 1.3 MB` 검사가 떨어진 까닭이 이것이었다). 다른 문서로 바뀌기 직전에 스크롤 위치를 문서 처음으로 돌린다(`leaveScrollPositionForNewDocument` — 문서의 주소가 바뀔 때, 줄바꿈 끔의 폭을 버리는 자리와 같다): 문서 처음은 어느 내용에서나 문서 안이고, 보던 곳은 그 뒤에 전과 같이 되살린다. 열기 17.5 s → 160 ms, 그 뒤의 JSON 정리 3.1 s → 166 ms. 분할 보기에서는 편집기마다 따로 돌린다(보조 편집기만 끝에 있어도 전환 292 ms — 둘 다 처음에 있을 때 281 ms). **같은 파일을 다시 읽을 때**(밖에서 바뀐 파일, 저장본으로 되돌리기, 열려 있는 파일을 다시 열기)는 처음으로 돌리지 않는다 — 덧붙여지는 로그를 읽는 중에 화면이 문서 처음을 스치면 안 된다. 그런데 파일이 짧아졌으면 그 위치가 역시 문서 끝 너머이고, 다시 읽기의 첫 배치 패스는 보던 곳을 되살리기(`EditorView.handleReload`) 전에 돈다(줄 인덱스 발행을 받은 첫 줄 발행이 밀린 배치를 끝낸다): 24,002줄 JSON 의 끝을 보는 중에 파일이 12,002줄로 다시 쓰이자 다시 읽기가 16.2 s(조각 표 +11,901), 그 뒤의 JSON 정리가 3.2 s 였다. 통째 교체가 문서 처음이 아닌 곳에서 일어났으면 적어 두었다가(`contentReplacedBeforeLayout`) 다음 `layout()` 앞에서 문서 끝을 묻고, 너머면 문서 안으로 들어온다 — 읽기 닻이 쓰는 것과 같은 탐침(`enterDocumentBeforeViewportLayout`)이다. 0.27 s / 0.15 s 가 됐고, 늘어난 파일은 끝 너머가 아니라 자리가 그대로며, 탐침과 되살리기 사이에 그려지는 프레임은 없다. **분할 보기에서 한 편집기가 문서를 통째로 바꿀 때**(모두 선택 + 도구·붙여넣기, 그 되돌리기·다시 실행)의 다른 편집기도 같은 처지다 — 스크롤 좌표는 그대로인데 높이 어림이 통째로 바뀌어 다른 줄을 보게 되고(24,000줄 문서의 12,002번 줄을 보던 편집기가 11,541번 줄로, 끝을 보던 편집기는 끝에서 2,275줄 위로), 끝에 있었으면 문서 전체를 배치할 수도 있다(조각 23,878개, 되돌리기 5.6 s → 7.2 s). 다시 읽기와 달리 그 편집기에는 뒤에서 자리를 되살려 줄 것이 없어, 끝 너머 탐침만 걸리면 끝에서 세 화면 위에 남는다. 문자 오프셋은 그런 편집을 넘기지 못하므로 보던 곳을 **줄(문단 번호 + 열)**로 잡아 두었다가(`captureReadingPlace`) 편집 뒤에 읽기 닻으로 같은 줄을 같은 높이에 되돌린다 — 줄 수를 지키는 도구에서는 같은 줄이고, 끝을 보고 있었으면 끝에 붙인다. 되돌리기·다시 실행에서는 편집기마다 제 자리를 잡아 두고, 캐럿을 따라간 편집기는 건드리지 않는다. 그리고 다음 턴에 한 번 더 맞춘다(`settleReadingPlace`): 통째 편집 뒤에는 구문 색 재검증이 다음 턴에 문서 전체의 배치를 한 번 더 무효화할 수 있어(주 편집기의 뷰포트가 아직 배치되기 전이면 범위를 줄이지 못한다), 한 번만 맞추면 끝에 붙여 둔 편집기가 그 뒤 패스에서 문서 전체를 배치했다(조각 +23,895, 1.8 s). '다른 편집기가 한 편집이면 탐침을 걸지 않는다'는 더 간단한 길은 그 편집기가 문서 전체를 배치하게 만들었다(가라앉기까지 2,254 ms). 저장소의 '전체가 바뀌었다'는 통지에 걸면 안 된다 — 모두 접기·펴기도 그렇게 알리므로, 처음 구현에서는 모두 펴기가 화면을 문서 맨 위로 던졌다(12707번 줄 → 107번 줄).
- **컨테이너가 뷰의 폭을 따르지 않으면 `-[NSTextView textContainerOrigin]` 이 읽힐 때마다 문서 전체를 배치한다**(macOS 27 실측: `ensureLayoutForRange:` 에 문서 범위 — 가로로 크기를 맞추든 아니든, 컨테이너 폭이 무한이든 유한이든 같다). 그 getter 는 뷰포트 배치(`_viewportBoundsForTextViewportLayoutController:`)·프레임 변경(`renewGState`)·캐럿 깜빡임·스크롤 준비(`prepareContentInRect:`)·이 앱의 캐럿 사각형 계산이 걸음마다 읽는다: 이미 배치된 1.3 MB 문서에서 한 번에 22~26 ms(줄바꿈 끔의 타이핑이 키당 13~16 ms 였던 까닭), 전체 속성 재적용(줄바꿈 전환·글자 크기·테마) 직후에는 2.1~2.4 s, 4 MB 로그에서는 조각 2,000개 상한이 그 배치를 걸음마다 버려 휠 한 걸음이 13~17 s·열기가 15 s 였다. 그런데 값은 늘 위·왼쪽 여백(`textContainerInset`) 그대로다(왼→오·오른→왼 문서와 아랍어 UI 에서 AppKit 의 값과 견줘 불일치 없음) — 줄바꿈 끔에서는 getter 를 재정의해 여백을 바로 돌려준다(`HyperTextView+NoWrap.swift`). 줄바꿈 끄기 1.7~3.4 s 정지 → 250 ms 넘는 정지 없음, 줄바꿈을 끈 4 MB 로그 열기 0.35 s·휠 3.7 ms/걸음.
- **TextKit 2 에서 AppKit 의 가로 자동 크기(`isHorizontallyResizable`)는 못 쓴다.** `_updateContentSizeIfNeeded` 는 문서에 따라 폭을 넓히지 않거나(3,000줄 문서: 가장 긴 줄 17,334 pt 인데 텍스트 뷰는 편집기 폭 740 pt 그대로 — 가로 막대가 없고, 줄 끝으로 가도 따라가지 않고, 멀리 있는 긴 줄에서 ⌘→ 를 누르면 화면이 문서 맨 위로 튄다) 내용과 상관없는 폭을 준다(가장 긴 줄 867 pt 인 메모에 1,644 pt). 그래서 폭은 뷰가 정한다: 편집기 폭과 지금까지 배치해 본 가장 넓은 줄 가운데 큰 쪽. 뷰포트가 배치될 때마다 재고(`fitNoWrapWidth` — 읽기만 한다), '보이게 스크롤' 앞에서는 대상이 지금의 폭 밖이면 먼저 넓힌다(`widenNoWrap` — 좁은 채로 AppKit 에 맡기면 가로로는 가지 못하고 세로 위치까지 틀어진다: 폭 740 pt 인 뷰에서 x 17,350 의 캐럿을 보이게 하자 화면이 y 0 으로 갔다). 컨테이너 폭은 무한 그대로 둔다 — **유한한 폭을 주면 오른쪽→왼쪽 문단(아랍어·히브리어)이 그 폭의 오른쪽 끝에 붙어 화면 밖으로 나간다**(무한일 때는 왼쪽 여백에서 시작한다). AppKit 은 왼쪽으로 한 글자씩 가다 가장자리를 넘는 걸음에서 한 번 늦는다(캐럿이 6.3 pt 가려진 채 한 걸음) → 스크롤 뒤 캐럿이 보이는 열 밖이면 그만큼만 가로로 민다(`revealNoWrapCaretColumn`).
- **줄바꿈 끔도 높이 추정 체제다.** 위의 전체 배치를 건너뛰므로 줄바꿈을 끈 문서도 배치하지 않은 문단의 높이는 어림이다. 다만 그려 둔 뷰포트에서 답하는 경로(`coveringViewport`·`firstVisibleParagraphOffset`·`firstVisibleParagraphAnchor`)와 줄 기준 손잡이는 여전히 자동 줄바꿈(`widthTracksTextView`)에서만 쓰고, 줄바꿈 끔은 점 질의 경로 그대로다.
- **높이 0 조각은 배치된 조각에만 통한다 — 접힌 문단은 콘텐츠 열거에서 뺀다.** 레이아웃 delegate 가 숨은 문단에 높이 0 조각을 돌려줘도, TextKit 2 는 배치하지 않은 구간의 높이를 문단 내용으로 어림한다(창 없는 실험: 30,000줄 중 27,000줄을 접은 문서의 끝을 실제 51,000 pt 가 아니라 537,651 pt 로 답했다 — 접지 않은 값 그대로). 배치한 조각은 2,000개까지만 붙들므로 접힌 큰 문서는 스크롤·리플로 패스마다 좌표가 수만 pt 씩 바뀌었다(접힌 1.3 MB 메모: 휠 걸음 평균 28 ms·최악 1.2 s, End 뒤 빈 띠, 글자 크기·사이드바 변경에 최대 1 s 정지). 숨은 문단을 `NSTextContentStorageDelegate` 의 `textContentManager(_:shouldEnumerate:options:)` 로 열거에서 빼면 레이아웃 매니저가 그 문단을 아예 보지 못해 조각도 어림도 없다(같은 문서가 52,760 pt). delegate 만으로는 모자란다: `NSTextContentStorage` 가 "숨길까"를 물으려고 숨은 문단마다 요소를 만들어 캐시에 넣고, 그 장부 정리(`__NSTextContentStorageFlushUncachedTextElements`)가 접힌 큰 문서의 배치 시간 대부분이었다(휠 한 걸음 18 ms) — 콘텐츠 스토리지 하위 클래스(`FoldingContentStorage`)가 `enumerateTextElements` 에서 숨은 구간을 만나면 열거를 멈추고 그 끝에서 다시 시작한다(29,990줄 접힘에 걸친 뷰포트 배치 8 → 0.13 ms; 접힘이 없으면 곧장 super). 결과: 같은 메모의 휠 걸음 약 8 ms, 리플로 정지 없음.
- **문서의 마지막 문단은 열거에 남겨야 한다.** 빠지면 `NSTextView` 가 문서 높이를 구하지 못한다(30,000줄 문서의 높이가 배치한 화면만큼인 629 pt 로 잡히고 End 키가 움직이지 않는다). 그 문단만은 높이 0 조각(`FoldedLayoutFragment`)으로 숨기는데, 조각이 0 이라 답해도 문서 높이에는 실제로 배치된 높이가 들어가므로(네 줄로 감긴 마지막 문단을 접자 마지막 보이는 줄 아래에 68 pt 가 비었다) 문단 요소도 0.01 pt 짜리 표시용 문단으로 바꿔 준다(`textContentStorage(_:textParagraphWith:)` — 글자 수는 같게, 끝의 개행은 공백으로: 개행으로 끝나면 빈 덧줄이 보통 줄 높이로 붙는다).
- **접힘 변경은 `edited(.editedAttributes)` 로 알린다.** `invalidateLayout(for:)` 만으로도 요소는 다시 열거되지만 뷰포트 위쪽 구간의 높이 어림이 옛 값으로 남는다(문서 끝에서 모두 펴면 510,000 pt 문서를 56,275 pt 로, 가운데에서 모두 접으면 51,000 pt 를 299,264 pt 로 본다). 속성 편집 통지는 그 구간의 어림을 버리고 이미 만든 조각도 다시 만들게 한다(문자열·undo·dirty 에는 영향이 없다).
- **끝까지 닿는 접힘이 펴진 직후, 마지막 문단의 조각은 접혀 있던 때의 자리에 남는다.** 머리 줄 바로 아래다 — 사이의 문단들은 열거된 적이 없고, TextKit 2 는 높이 어림을 다시 잡기 전까지 그 조각을 거기 둔다. 그 자리는 화면 안이라 AppKit 은 문서 끝을 "이미 보인다"고 보고 스크롤하지 않는다: 12,001줄을 한 줄 아래로 접고 ⌘↓ 하면 접힘은 펴지고 캐럿은 문서 끝인데 캐럿 상자의 y 가 36 pt, 화면은 맨 위 그대로였다(명령으로 편 직후의 ⌘↓ 도 같다). 높이 어림이 이미 실제와 맞는 문서(짧은 줄)에서만 드러난다 — 어림이 틀린 문서는 배치하는 동안 다시 잡히며 풀린다. 그래서 앞에서 무엇을 스크롤했는지에 달렸다: 전체 묶음에서는 매번, 그 시나리오만 돌리면 0번(`--only scroll-knob-state,fold-giant` 로 본다). AppKit 에 '보이게 스크롤'을 맡긴 직후 좌표가 아니라 **그려 둔 뷰포트로** 확인한다(`revealDocumentEndIfMissed`): 대상이 마지막 문단인데 그려 둔 범위가 거기 닿지 않고 화면도 문서 끝이 아니면, 읽기 닻으로 뷰포트를 배치해 가며 끝에 붙인다. 하네스 쪽 교훈: 캐럿이 보이는지를 캐럿 상자의 좌표로 묻는 검사(`checkCaretVisible`)는 같은 낡은 좌표에 속는다 — 문서의 끝·처음에 닿았는지는 그려 둔 조각으로 보는 `expectBottom`/`expectTop` 으로 본다.
- **AppKit 의 캐럿 이동은 열거되지 않은 구간을 건너뛴다.** 숨은 문단이 배치에 없으므로 ← 는 접힘 아래 줄 머리에서 머리 줄 끝으로, ⇧↓ 는 머리 줄에서 접힘 다음 줄로 간다(접힌 내용이 보이지 않는 채 선택에 들어간다). 걸음 **뒤에** 바로잡는 것(`stepIntoFold` — 논리적으로 이웃한 글자 ±1 이 숨어 있는데 AppKit 이 건너뛰었으면 그 자리에 놓는다)만으로는 모자란다: 단어·문단 걸음은 이웃 글자가 보이는 자리에서도 닫힌 접힘을 통째로 넘는다. 접힌 머리 줄 `def third(z):` 의 z 뒤에서 ⇧⌥→ 가 접힘 아래 줄의 첫 낱말까지 고르고(접힘은 닫힌 채), 이어진 ⌫ 가 숨은 두 줄을 지웠다(225 → 184자; 편 문서에서는 213). 그래서 걸음 **앞에서** 미리 편다(`openFoldsInReach`): 그 걸음이 다 편 문서에서 닿을 글자를 문자열에서 구해(배치에 묻지 않는다 — 글자 ±1, 낱말의 끝·머리, 줄·문단의 끝·머리, ⇧↑/⇧↓ 는 이웃 줄의 같은 열까지) 숨은 것이 있으면 그 접힘을 먼저 펴고, AppKit 이 숨은 줄이 있는 배치에서 걸음을 계산하게 한다 — 편 문서에서 같은 키를 누른 것과 같은 자리이고 선택의 방향도 그대로다("캐럿이 숨은 줄로 들어가면 편다"는 전과 같은 동작). 선택을 늘리는 걸음은 닿는 범위의 숨은 문단을 **전부** 본다 — 고를 글이 모두 화면에 보여야 한다: 구간마다 첫 숨은 문단만 보던 때에는 겹친 접힘에서 바깥 것만 펴져, 낱말 없는 안쪽 머리 줄(JSON 의 `[`·`{` 줄)을 가진 바깥 머리 줄 끝의 ⇧⌥→ 가 아직 닫힌 안쪽 접힘 너머까지 고르고 ⌫ 가 그 숨은 줄을 지웠다(76 → 7자; 편 문서에서는 38). 선택 없는 걸음은 캐럿이 놓일 자리를 숨기는 접힘만 편다(지나치는 접힘은 닫힌 채). ←/→ 로 이름 붙은 명령은 화면에서의 방향이라 문단의 쓰기 방향을 따른다(`writingDirections` — 문단 스타일, 없으면 첫 강한 방향 글자): 오른쪽→왼쪽 문단에서 ⌥← 는 글의 뒤쪽으로 나아가는데 명령 이름만으로 방향을 정하던 때에는 반대쪽을 살펴, 접힌 히브리어 제목 끝의 ⇧⌥← 가 닫힌 접힘 너머를 고르고 ⌫ 가 숨은 구역을 지웠다(112 → 60자; 편 문서에서는 106). 두 방향의 글자가 섞인 문단은 양쪽을 다 본다(화면 방향이 캐럿 아래의 런에 달려 있다 — 필요 이상으로 펼 수 있다). 선택을 늘리는 중에 어느 끝에서 걸음이 출발하는지는 직전 걸음이 옮긴 끝을 적어 두어 안다(`caretStepHead` — 걸음 전후에 그대로인 끝이 닻이다. 걸음 밖에서 선택이 놓이면 버린다): 모르면 두 끝을 다 볼 수밖에 없는데, 그러면 닻이 접힘 옆에 있는 선택을 **줄이는** 키가 그 접힘을 폈다(접힌 머리 줄 끝에서 ⇧← 세 번 뒤의 ⇧⌥→). 끌어서 고른 선택은 여전히 머리를 몰라 양 끝을 본다. 머리 줄의 개행까지만 닿는 걸음(머리 줄 끝의 ⇧→, 0열에서의 ⇧↓)은 숨은 글자에 닿지 않으므로 펴지 않는다 — `stepIntoFold` 는 그 경계를 위해 남아 있다. 선택 없는 ↑/↓ 는 전처럼 접힘을 건너뛰는데(`moveAcrossFold`), 문단의 마지막(↓)·첫(↑) **화면 줄**에서만 그렇게 한다(`screenLine(at:)`): 문자열의 줄로만 보면 감긴 접힌 머리 줄의 첫 화면 줄에서 ↓ 한 번에 접힘 아래로 가, 머리 줄의 나머지 화면 줄에는 키보드로 갈 수 없었다. 줄·문단의 끝이나 머리로 가는 명령(⌘→ ⌘← ⌃E ⌃A 와 ⇧ 변형)이 캐럿을 못 움직인 것은 한 걸음이 아니다 — 캐럿이 이미 거기 있는 것이라 접힘 안으로 들여놓지 않는다(들여놓았더니 접힌 머리 줄 끝에서 ⌘→ 를 한 번 더 누른 것만으로 접힘이 펴지고 다음 글자가 첫 숨은 줄에 들어갔다). 선택 변경 감시는 네이티브 선택(머리 캐럿)만이 아니라 열 블록의 행과 추가 캐럿도 본다 — 블록은 문자열의 줄을 세므로 접힘을 가로질러 늘리면 숨은 줄마다 행이 생기고, 접힌 채 두면 다음 키가 화면에 없는 줄들을 고친다. 다만 그 범위들이 네이티브 선택과 맞을 때만 본다: 여러 캐럿의 편집 도중에 오는 선택 통지에서는 그 범위들이 아직 편집 전 오프셋이고 접힘은 이미 편집 뒤 좌표라, 접힘 위의 글이 줄어드는 편집이 그 접힘을 까닭 없이 폈다. 영역 다시 스캔과 탭 복귀의 접힘 되살리기는 캐럿뿐 아니라 선택의 양 끝·열 블록의 행·추가 캐럿이 놓인 줄도 접어 숨기지 않는다.
- **접힘은 문서 단위다.** 열거는 콘텐츠 스토리지의 일이라 분할한 두 편집기(레이아웃 매니저만 따로)가 접힘을 같이 쓴다(`FoldStore`). 접힘이 바뀌면 그 문서를 보이는 편집기마다 읽기 닻을 잡았다 되돌린다: 명령을 내린 편집기의 모두 접기·펴기는 캐럿 줄이 보이면 그 줄(접혀 사라지면 그 머리 줄이 같은 높이에), 그 밖에는 맨 위 줄. 맨 위 줄을 지키던 때에는 모두 펴기가 그 줄과 캐럿 사이의 접힘을 펴며 캐럿 줄을 화면 밖으로 밀었다(195.7 → 771.7 pt, 화면 382 pt). 숨겨진 캐럿은 머리 줄 끝으로 옮기되 명령을 내린 편집기만 따라 스크롤한다. 편집은 두 편집기에서 통지되지만 접힘은 한 번만 옮긴다(`FoldStore.textWillChange`). 명령이 아니라 **편집이나 다시 스캔이 접힘을 펼 때**(다음 턴으로 미뤄진 다시 배치 — 접힌 구역 바로 아래에 쓴 줄은 그 구역에 속하게 되므로, 쓰고 있는 줄을 숨기지 않으려면 구역을 펴야 한다)는 키 입력을 받고 있는 편집기(`focusedController`)가 캐럿 줄에 닻을 내린다: 맨 위 줄을 지키면 치던 줄이 펴진 구역의 높이만큼 내려간다(60줄 구역 아래에서 치던 줄이 382 pt 화면의 y 1524 로 — 다시 스캔이 펴는 쪽에서 잰 것이다. 편집이 직접 편 접힘의 줄들은 그 편집 직후의 첫 배치에서 이미 놓이므로, 한 턴 뒤의 다시 배치 쪽 닻은 화면을 바꾸는 경우를 재현하지 못했다 — 같은 규칙으로 맞춰 둔 것). 분할의 다른 편집기는 맨 위 줄 그대로다. **되돌리기·다시 실행**은 `shouldChangeText` 를 거치지 않아 사후 통지로 전하는데, 닫힌 접힘이 없어도 옮길 것(접기 후보, 아직 다시 배치하지 않은 범위)이 있으면 전해야 한다(`tracksUndoEdits`): 안 전하면 접힘 없는 문서에서 ⌘Z 뒤 다음 스캔까지(약 300 ms) 후보가 옛 오프셋에 남아 거터 화살표가 사라지고 접기가 밀린 줄을 접었으며, 되돌리기 묶음(저장소 편집 여러 번으로 재생된다)의 첫 편집이 마지막 접힘을 편 뒤의 편집들이 '다시 배치할 범위'를 옮기지 못해 문서 끝까지 닿던 접힘의 마지막 문단이 높이 0 조각으로 남았다(파일의 마지막 줄이 안 보임). 비용 차이는 없다(1.3 MB 에서 한 글자 되돌리기 0.5~1.4 ms).
- **문서 높이 어림은 뷰포트를 배치할 때마다 다시 잡힌다 — 손잡이는 줄 기준으로.** 한 번도 안 본 곳으로 한 화면 넘게 뛰면 걸음마다 ±10~20 % 가 흔들린다(1.3 MB 메모: 847,845 … 1,157,051 pt, 실제는 약 70만; 세션 초반, 배치해 본 문단이 적을수록 크다). `NSScrollView` 는 손잡이를 "스크롤 위치 ÷ (문서 높이 − 화면 높이)"로 놓으므로 800 pt 휠 250걸음 중 95번 손잡이가 거꾸로 갔다(최대 14.6 pt / 382 pt 트랙). 줄 수는 정확히 아니까(`liveLineIndex`) 손잡이 값을 "화면 위로 지나간 문단 수 ÷ (그것 + 화면 아래에 남은 문단 수)"로 놓는다(`EditorScrollView.swift`) — 같은 화면에는 늘 같은 값, 처음 0·끝 1. `NSScroller` 하위 클래스의 함정 둘: 스크롤러의 `enclosingScrollView` 는 nil 이다(스크롤 뷰의 문서 쪽 자식이 아니라서 — `superview` 로 찾는다), 그리고 하위 클래스는 `isCompatibleWithOverlayScrollers` 를 재정의하지 않으면 겹침(overlay) 스타일에서 빠진다.
- **반응형 스크롤(트랙패드 제스처)과 `NSApp.currentEvent`.** 위상(phase)이 붙은 제스처는 `NSScrollView` 가 began 이벤트에서 추적을 시작해(`NSScrollingBehaviorConcurrentVBL`) 뒤따르는 이벤트를 큐에서 직접 꺼내 가고, 화면 주사율마다 main 스레드에 동기화한다. 그 동기화 블록에서 오는 live scroll 알림에는 `NSApp.currentEvent` 가 없다 — 알림마다 "지금 이벤트가 위상 있는 스크롤인가"를 다시 가리면 첫 움직임에서 '제스처 아님'이 되어 끝 클램프가 탄성과 싸운다(끝을 넘겨 당기는 동안 프레임마다 16~82 pt 씩 거꾸로 튀고, 손을 뗀 뒤 문서 끝에서 5~71 pt 못 미친 곳에 멈췄다). 제스처인지는 **시작 알림에서만** 가리고 끝 알림까지 유지한다(`EditorView.Coordinator.liveScrollIsGesture`). AppKit 의 관성을 멈출 공개 수단은 없다: 관성 중에 입력·방향키가 화면을 캐럿으로 데려와도 남은 관성이 다시 끌고 간다(친 글자가 1,375 pt 밖) — 제스처 중에 '보이게 스크롤'이 요청됐으면 제스처가 끝난 뒤 캐럿이 안 보일 때 한 번 더 데려온다(`liveScrollDidEnd`). **합성 제스처**(실사용 하네스): 이벤트를 `scrollWheel(with:)` 에 하나씩 건네면 began 뒤가 무시되고 live scroll 에 갇힌다(320 pt 중 18 pt 만 움직임), 실시간 간격으로 큐에 넣어도 같다(추적기는 시작할 때 큐에 있던 것만 꺼낸다). 손가락 구간 전체(began → changed… → ended)를 `NSApp.postEvent` 로 앱 자신의 큐에 **한꺼번에** 넣으면 추적기가 꺼내 가고, 그 뒤의 관성·탄성은 AppKit 이 실제 트랙패드와 같은 경로로 실시간으로 돌린다(관성 이벤트는 넣지 않는다 — 넣으면 삼키고 관성 없이 끝난다). 합성 이벤트에는 창이 없어 하네스의 로컬 모니터가 스크롤 뷰에 건넨다. 그래서 '손가락을 천천히 끄는 동안'은 재현하지 못한다(`RealUse+Trackpad.swift`).
- 스크롤 위치를 바로잡는 장치가 여럿이다 — 건드릴 때는 함께 본다: 편집 뒤 덮임 확인(`coverViewportAfterEdit`), 그리기 중 질의 지킴이(`guardingViewport`), 문서 끝·처음 클램프(`constrainScrollToDocumentEnd`), 읽기 닻(리플로), 스크롤 닻(그 밖의 배치 패스). 지킴이가 재배치를 일으켜야 닻이 화면을 지키므로 둘은 합칠 수 없다. 2026-11-25 에 더해진 것 — 언제 켜지고 무엇과 겹치지 않는가:
  - **입력 뒤 한 줄 밀기**(`revealCaretStep(afterEdit:)`): `insertText`·`setMarkedText`·`insert…`/`delete…` 명령이 부른 `scrollRangeToVisible` 안에서만(`editRevealDepth > 0`). 방향키의 한 줄 밀기와 같은 함수이고, 처리했으면 AppKit 의 가운데 맞춤을 부르지 않는다(둘 중 하나만 돈다). 어느 쪽이든 '보이게 스크롤'이라 스크롤 닻은 다음 패스를 쉰다(`blockLayoutAnchor`). 큰 편집·화면 위에서 시작한 편집·문서 마지막 줄에서는 꺼져 있다(AppKit 으로). 줄바꿈 끔에서도 돈다 — 세로만 옮기고, 가로는 아래 '줄바꿈 끔의 폭 관리'가 이어서 맞춘다. 매크로 재생 중에는 걸음마다 돌지 않고(`isReplayingMacro` — 방향키의 한 줄 밀기도), 재생이 런루프에 양보하기 직전과 끝에서 `revealCaretAfterReplaySteps` 가 한 번씩 대신한다: 문서 끝 너머 탐침 → 뷰포트 배치 → 방향키 규칙.
  - **큰 편집 뒤 캐럿 확인**(`revealCaretAfterRelayout`): 위의 한 줄 밀기가 캐럿이 편집 시작에서 64 문단 넘게 떨어졌다고(`tooFar`) AppKit 에 넘긴 편집의 다음 턴에 한 번 — 배치를 끝낸 뒤 캐럿이 안 보이면 그리로 스크롤한다(자리가 실측으로 바뀌며 한 번 더 어긋날 수 있어 두 번까지). 선택이 있거나 멀티 캐럿이거나 문서를 통째로 바꾼 편집이면 하지 않는다. 같은 함수를 큰 범위가 돌아오는 실행 취소와 거터 폭이 바뀌어 본문이 다시 감길 때가 전부터 쓴다. 긴 선택(`longRevealLength` = 16,384 단위 이상 — 되돌린 범위 전체가 다시 골라진 것)은 '보이게 스크롤'에 통째로 넘기지 않는다: AppKit 이 그 범위를 전부 배치한다(1.3 MB 문서 전체가 골라진 채 7.5 s). 문서 전체이거나 화면이 이미 그 범위 안이면 그대로 두고, 아니면 범위의 처음만 보인다.
  - **제스처 끝의 캐럿 되찾기**(`liveScrollDidEnd`): 트랙패드 제스처(관성 포함) 중에 **캐럿을 보이게 하려는** `scrollRangeToVisible` — 입력·캐럿 걸음이 부른 것, 또는 대상이 선택 범위에 닿는 것(찾기 점프) — 이 불렸을 때만 표시해 두었다가(`revealAfterLiveScroll`; 읽던 곳을 되살리는 스크롤은 `scrollToReadingPlace` 로 불러 대상이 캐럿 자리와 같아도 세지 않는다), 끝 알림에서 끝 클램프를 먼저 돌린 뒤 캐럿 줄이 안 보이면 한 번 스크롤한다. 제스처 중에는 끝 클램프가 쉰다 — 둘 다 끝 알림 하나에서 차례로 돈다. 표시는 그 제스처 안에서만 산다: 다음 스크롤이 시작되거나(`liveScrollWillStart`) 문서가 통째로 바뀌면 버린다. 끝 알림이 빠진 제스처의 표시가 남으면 나중의 아무 스크롤 끝에서 — 손잡이 끌기도 live scroll 시작·끝 알림을 낸다 — 화면이 캐럿으로 튀었고(손잡이를 40 pt 끌고 놓자 끌기 전의 캐럿 줄로), 탭으로 돌아와 읽던 곳을 되살리는 스크롤까지 표시를 켜면 관성 중에 탭을 바꿨을 때 돌아간 탭이 캐럿으로 갔다(읽던 1059번 줄 대신 295번 줄). 범위만으로 '캐럿을 향한 요청'을 가릴 수는 없다: 캐럿이 읽던 곳의 맨 위 문단 머리에 있는 탭(문서 처음을 보던 탭)에서는 되살리는 대상이 곧 캐럿 자리라, 관성 중에 그런 탭으로 바꾸자 남은 관성이 새 탭을 2,839 pt 굴린 뒤 제스처 끝에 화면이 캐럿으로 되돌아갔다 — 그래서 부르는 쪽이 밝힌다.
  - **문서 끝 너머 진입**(`enterDocumentBeforeViewportLayout`): 스크롤 위치가 마지막 조각 아래에 있을 때만 움직이고, 세 군데서 부른다 — `restoreReadingAnchor` 의 첫 패스(리플로), 내용이 통째로 바뀐 뒤의 첫 `layout()` 앞(`contentReplacedBeforeLayout` — 같은 파일을 다시 읽었을 때, 그리고 분할의 다른 편집기가 문서를 통째로 바꾸거나 되돌렸을 때; 문서 처음이 아닌 곳에 있을 때만), 매크로 재생 뒤의 캐럿 보이기 앞. 끝 클램프와는 기준이 다르다 — 클램프는 텍스트 뷰의 프레임(클립 뷰가 허용하는 범위)을, 이것은 레이아웃 매니저가 지금 보는 끝(마지막 조각의 아래 가장자리)을 본다. 자리를 맞추는 것은 뒤따르는 읽기 닻 루프다.
  - **문서 전환 때 처음으로**(`leaveScrollPositionForNewDocument`): 문서의 주소가 바뀔 때(탭 전환·파일 열기)만, 내용이 바뀌기 직전에 스크롤 위치를 y 0 으로. 자리는 뒤따르는 보기 위치 복원(`EditorView.restoreViewStateIfNeeded`)이 잡는다. 같은 파일 다시 읽기·접기·리플로에서는 돌지 않는다 — 위의 '문서 끝 너머 진입'과 같은 함정을 다른 입구(리플로가 아니라 문서 교체)에서 막는 것이라 둘이 겹치지 않는다. 다시 읽기는 위치를 지켜야 하므로 처음으로 돌리는 대신 '문서 끝 너머 진입'이 맡는다(문서 처음에 있으면 볼 것이 없어, 이 장치가 돈 뒤에는 그쪽이 돌지 않는다).
  - **AppKit 에 맡긴 '보이게 스크롤' 직후의 두 확인**(`revealDocumentEndIfMissed`·`revealTopInsetWithDocumentStart`): 한 줄 밀기가 처리하지 않아 `super.scrollRangeToVisible` 을 부른 걸음에서만, 그 바로 뒤에. 앞의 것은 대상이 마지막 문단인데 그려 둔 뷰포트가 거기 닿지 않았을 때 끝에 붙이고(위 '끝까지 닿는 접힘'), 뒤의 것은 문서의 맨 처음을 보이라고 했는데 화면이 위 여백 안쪽에 멈췄을 때 y 0 까지 올린다 — AppKit 은 첫 줄의 상자가 화면에 들어오는 데서 멈춰, 아직 배치되지 않은 곳에서 올라오면(통째 편집을 되돌린 뒤의 ⌘↑) 여백 12 pt 가 잘린 채 남았다. 둘 다 조건이 맞을 때만 움직이고 그 밖의 걸음에는 읽기만 한다.
  - **분할의 다른 편집기 자리 지키기**(`captureReadingPlace` → `settleReadingPlace`): 문서를 통째로(절반 넘게) 바꾸는 편집과 그 되돌리기·다시 실행에서만. 편집한 쪽이 다른 편집기들의 보던 줄을 편집 전에 잡아 두었다가 편집 뒤에, 그리고 다음 턴에 한 번 더 읽기 닻(`restoreReadingAnchor` — 끝 너머 탐침 포함)으로 되돌린다. 되돌리기에서는 편집기마다 제 자리를 잡고, 캐럿을 따라간 편집기는 뺀다. 같은 파일 다시 읽기의 탐침(`contentReplacedBeforeLayout`)과 겹치는 자리다: 통째 편집도 통째 교체로 통지되어 그 탐침이 다른 편집기에 걸리는데, 자리를 되살리는 것은 이 장치다.
  - **줄 기준 손잡이**(`EditorScrollView.syncLineScroller`): 스크롤이 반영될 때와 `layout()` 의 끝에서 손잡이의 **값만** 놓는다 — 스크롤 위치는 건드리지 않으므로 다른 장치와 다툴 것이 없다. 손잡이를 끌 때만 `scrollToLineValue` 가 읽기 닻과 같은 경로(`restoreReadingAnchor`)로 스크롤한다. 줄바꿈 끔·접힌 문서·끝을 넘겨 당기는 중에는 AppKit 의 값 그대로다.
  - **줄바꿈 끔의 폭 관리**(`fitNoWrapWidth`·`widenNoWrap`·`revealNoWrapColumn`·`revealNoWrapCaretColumn`): 프레임 폭과 가로 위치(`clip.bounds.minX`)만 다룬다 — 세로 장치들은 `minX` 를 그대로 두고 옮긴다. '보이게 스크롤' 뒤의 가로 맞춤은 둘 중 하나다: 한 줄 밀기가 세로를 직접 민 걸음이면 `revealNoWrapColumn`(AppKit 을 부르지 않았으므로 가로를 여기서 다 맞춘다 — 방향키 걸음은 움직인 쪽 끝, 편집이 남긴 선택은 끝 → 시작 순으로 범위 전체), AppKit 이 스크롤한 걸음이면 `revealNoWrapCaretColumn`(가장자리에서 한 걸음 늦을 때 캐럿이 가려지지 않게만). `setFrameSize` 에서 폭을 이 값으로 고정하므로, 폭이 바뀔 때 읽기 닻을 자동으로 잡는 경로(자동 줄바꿈 전용)는 줄바꿈 끔에서 돌지 않는다.

### 한글 폭 보정
- AppKit은 캐스케이드 리스트에 지정한 폴백 폰트의 **크기를 무시한다**(실측). 그래서 한글 런마다 `.font` 속성으로 ×1.2 폰트를 직접 지정한다.
- MB 단위 텍스트에서 `NSRegularExpression`으로 한글 런을 찾으면 느리다. `unichar`를 64 K 청크로 직접 스캔해 런마다 `addAttribute`한다.
- 줄바꿈 종류 판별도 `String.contains("\r")`는 grapheme 단위라 1.3 MB에 80 ms가 들었다. UTF-8 바이트 스캔으로 1 ms 미만.

### 성능 메모 1 — 키 입력 지연
- 증상: 리본·패널이 키 입력마다 다시 그려졌다. 원인은 문서 상태를 `AppModel`을 통해 전달한 것.
- 조치: 캐럿 상태를 `EditorCaret`로 분리해 상태바·아웃라인·타임라인만 구독. 줄 인덱스는 `NSString` 버퍼 스캔, 저장은 불변 사본으로 백그라운드 쓰기. 셀프테스트에 `perf typing … ms/keystroke` 벤치마크 포함.
- 결과: 1.3 MB·3만 4천 줄 벤치마크 문서에서 키 입력당 약 3 ms(런루프 포함).

### 성능 메모 2 — 파일 전환
- 증상: 사이드바에서 파일을 바꿀 때 큰 문서는 120 ms 이상, 몇 번 전환하면 2 KB 파일도 600~800 ms 멈췄다.
- 원인 두 가지: ① 줄바꿈 판별의 grapheme 스캔(위), ② 파일마다 새 스토리지를 만들어 갈아끼운 것(위).
- 조치: `MemoDocument.switchTo(url:)` / `BookmarkStore.switchTo`로 제자리 전환. 계측 도구 `--debug-perf [--debug-perf-log <path>]`(구간 시간 + 메인 스레드 120 ms 이상 정지 감시), `--selftest-open`(작은 파일↔큰 파일 전환 벤치 + dirty 상태 전환 저장 정확성 검사, 가리킨 파일을 수정하므로 사본에서만).
- 결과: 큰 문서 전환 170~770 ms → 약 100 ms, 2 KB 파일 약 90 ms, 반복 전환 시 정지 0. 남은 비용 약 70 ms는 텍스트 뷰 뷰포트 레이아웃(CoreText 셰이핑).

### v0.6 메모 — 분할·undo·접기·매크로·전역 단축키
- **`NSTextStorage` 는 TextKit 2 관찰자(`NSTextContentStorage`)를 하나만 허용한다.** 분할 보기는 문서 스토리지에 콘텐츠 스토리지 하나를 붙이고 뷰마다 `NSTextLayoutManager` 만 추가한다(`EditorSession`). undo 는 `NSUndoManager` 하나를 모든 뷰가 쓰고, 포커스가 다른 뷰로 옮겨지면 입력 그룹 병합을 끊는다. 접힘도 콘텐츠 스토리지에 딸려 두 뷰가 같이 쓴다(2026-11-25 재설계 — 위 'TextKit 2'). 분할을 닫은 보조 편집기는 공유 undo 스택에 그 뷰의 항목이 남아 있는 동안 살려 둔다.
- **macOS 27 TextKit 2 의 undo/redo 는 `shouldChangeText`/`didChangeText` 를 부르지 않는다**(실측). dirty·자동 저장·줄 인덱스 갱신·북마크 이동은 `MemoDocument.textStorage(_:didProcessEditing:)` 에서 건다. 프로그램적 전체 교체(`programmaticReplaceDepth`)는 제외하고, 뷰 경로의 `textDidChange()` 와 겹쳐도 예약 취소·재예약뿐이라 비용이 없다.
- **접기는 숨은 문단을 콘텐츠 열거에서 뺀다**(2026-11-25 재설계 — 위 'TextKit 2' 의 접기 항목들). v0.6 부터 그때까지는 `NSTextLayoutManagerDelegate.textLayoutManager(_:textLayoutFragmentFor:in:)` 가 숨은 문단마다 높이 0 조각(`FoldedLayoutFragment`)을 돌려줬다; 지금 그 조각은 열거에 남기는 문서의 마지막 문단에만 쓴다. 접힘이 바뀌면 그 범위에 `edited(.editedAttributes)` 를 알린다. 접힘 오프셋은 `HyperTextView.onTextWillChange`(저장소 변경 직전)에서 즉시 옮기므로 줄 인덱스의 250 ms 지연과 무관하다. 후보 영역은 `FoldScanner` 가 백그라운드에서 계산한다.
- **AppKit 은 NSEvent 처리가 끝날 때만 자동 undo 그룹을 닫는다.** `Task.sleep`·런루프 양보·타이머로는 닫히지 않는다(실측). 프로그램적으로만 편집하는 셀프테스트는 `SelfTest.pumpEvent()`(빈 `applicationDefined` 이벤트 게시)를 `wait()` 마다 흘려야 대화형 사용과 같은 undo 단위가 된다 — 없으면 ⌘Z 한 번이 여러 단계를 되돌려 매크로·분할 검사가 틀린다.
- **모두 바꾸기 5,000건의 undo 가 1.7 s 걸렸다.** AppKit 의 `shouldChangeText(inRanges:)` undo 는 범위마다 `replaceCharacters` 를 다시 돌리고 매번 속성 런 배열을 memmove 한다(`NSMutableRLEArray`). `HyperTextView.performReplacements` 가 모든 범위를 한 번에 되돌리는 undo 를 직접 등록해 0.25 s. redo 도 같은 경로. 같은 종류의 비용이 범위 하나를 통째로 바꾸는 텍스트 도구에도 있었다 — `insertText` 로 넣으면 AppKit 의 입력 되돌리기가 지운 글을 속성 문자열로 되넣는다(1.3 MB 전체 주석 토글의 ⌘Z 5.3 s). 16,384 단위 이상의 범위는 같은 일괄 길로 보낸다(`replaceForTool`, 2026-11-26 — §3 '큰 범위를 바꾸는 도구의 편집').
- **키 입력마다 SwiftUI 가 다시 평가되던 곳 세 군데**: `isDirty = true` 재대입(값이 같아도 `@Published` 는 발행한다), 검색 패널이 `EditorCaret` 전체를 구독, 아웃라인·타임라인도 같은 구독. 각각 한 번만 설정·히트 목록만 구독·`$line.removeDuplicates()` 로 바꿨다. `NSFontManager.availableFontFamilies` 는 테마 적용마다 세 번 불려 캐시했다(`kCTFontManagerRegisteredFontsChangedNotification` 으로 무효화).
- **Carbon `RegisterEventHotKey`** 는 손쉬운 사용 권한 없이 동작하고 다른 키 입력을 보지 않는다. 다른 앱이 같은 조합을 먼저 등록했으면 `eventHotKeyExistsErr`(-9878) 로 실패해 상태바에 알리고, 시스템 단축키(입력 소스 전환 ⌃Space 계열)와 겹치면 오류 없이 시스템이 먼저 가로채므로 설정 화면에 안내만 둔다.
- **JSON 정리는 자체 재귀 하강 파서**다. `JSONSerialization` 은 키 순서를 바꾸고 `1.0` 을 `1` 로 만든다. BOM·뒤따르는 쉼표·주석(JSONC)을 받아 엄격한 JSON 으로 쓰며 5.6 MB 를 약 30 ms 에 처리한다. 오류는 `줄:열` 로 보고하고 캐럿을 옮긴다.

### 창 복구
- 같은 앱 인스턴스가 떠 있는 상태에서 LaunchServices가 새 인스턴스를 띄우면 SwiftUI가 기본 창을 만들지 않는 경우가 있다. `AppDelegate`가 0.4초 뒤 창이 없으면 '다시 열기(`rapp`)' 애플 이벤트를 자신에게 보내 `WindowGroup` 창을 연다.
- **SwiftUI `WindowGroup` 은 밖에서 온 열기 이벤트(`application(_:open:)`)마다 창을 하나 더 만든다**(실측). 모델·문서가 하나인 이 앱에서는 같은 문서에 편집기가 둘 붙는다(받는 곳이 없던 v0.10.7 까지는 요청한 파일도 열리지 않았다). `.handlesExternalEvents(matching: [])` 로 그런 이벤트가 창을 만들지 않게 하고, 파일은 `AppDelegate` 가 받아 탭으로 연다(`ExternalOpen.swift`).
- **열기 요청은 창보다 먼저 온다.** 앱이 꺼져 있다가 파일과 함께 뜨면 열기 콜백은 `applicationDidFinishLaunching` 보다 먼저, 창이 생기기 전에 불린다. 모델(첫 문서·지난 세션의 탭)은 그보다도 먼저 만들어져 있어 모델 수준에서 바로 연다 — 편집기는 나중에 그 문서에 붙는다. 그 순서는 SwiftUI 의 사정이라, 모델이 아직 없으면 만들어진 직후(`ExternalOpen.modelReady`)에 연다.
- **실행 인자의 파일은 앱이 직접 가른다.** AppKit 은 맨 인자를 `application(_:open:)` 이 아니라 옛 `application(_:openFiles:)` 로, 인자마다 한 번씩 넘기는데 그 판정이 이 앱의 옵션과 어긋난다. 한 줄표로 시작하는 인자마다 그 뒤의 (한 줄표로 시작하지 않는) 인자를 값으로 짝짓고 남는 것을 "열 파일"로 넘기므로(`NSTreatUnknownArgumentsAsOpen`), 값을 받는 옵션의 **값**이 파일이라며 넘어오고(`--realuse-out <폴더>` 의 폴더, `--realuse-only <목록>` 의 목록 — 없는 경로를 열면 빈 파일이 만들어진다), 값 없는 옵션 바로 뒤의 파일은 그 옵션의 값으로 삼켜져 넘어오지 않는다(`--quit a.md`). 그래서 실행 인자를 우리 문법으로 가른다(`LaunchOptions.parse`): 값을 받는 옵션의 목록(`LaunchOptions.valueOptions`)과 값이 있어도 없어도 되는 옵션(`optionalValues` — `--split` 은 뒤의 인자가 분할 방식일 때만 값)에 있는 것만 뒤의 인자를 값으로 삼고, 한 줄표 하나로 시작하는 시스템 옵션(`-AppleLanguages (ko)`)은 늘 `-키 값` 쌍이며, **그 밖의 맨 인자는 어디에 있든 열 파일이다**(`HyperEdit a.md --ephemeral b.md` → a.md, b.md). 모델이 만들어질 때 한 번 받아(`ExternalOpen.takeLaunchFiles`) 다음 턴에 한꺼번에 연다. `LaunchOptions.value(_:)` 도 목록의 옵션에만 값을 돌려주므로, 새 옵션을 목록에 넣지 않으면 그 옵션이 아예 먹지 않아 바로 드러난다(빠진 채 동작하면 그 값이 열 파일로 읽힌다). AppKit 이 넘긴 것은 견주기만 한다 — 우리 문법으로 옵션의 값인 것은 열지 않고 stderr 에 `[open] not a file to open: …` 로 적는다.
- **미해결 — 편집기 창만 닫혀 있을 때 밖에서 온 파일.** 설정 창이 떠 있어 앱이 살아 있는 동안 편집기 창을 닫아도 그 `NSWindow` 와 SwiftUI 내용은 남는다(보이지 않을 뿐). 열기 요청을 받으면 `ExternalOpen.showWindow` 가 그 창을 `makeKeyAndOrderFront` 로 다시 보이므로 창이 하나 더 생기지는 않고, 편집기·사이드바·상태바는 새 문서를 보인다. 그런데 SwiftUI 는 닫힌 창의 장면을 사라진 것으로 둔다: 닫는 순간 `ContentView` 의 `.task` 가 취소되고, 탭 줄(`DocumentTabBar`)의 `onGeometryChange` 가 그 뒤로는 불리지 않는다 — 자동화에서 그 창을 AppKit 호출로만 다시 보였을 때 탭은 셋인데 탭 줄에는 닫힐 때의 하나만 보였고, 그 뒤에 연 파일의 탭도 나오지 않았다. 사람이 쓰는 실행에서도 그런지는 자동화로 볼 수 없어(비활성 실행에서는 `makeKeyAndOrderFront` 를 부르지 않는다) 손으로 확인해야 한다. 제대로 고치려면 편집기 장면을 단일 `Window` 로 바꿔 `openWindow` 로 다시 열거나, 다른 창이 떠 있을 때의 닫기를 숨기기(`orderOut`)로 바꾸거나, 탭 줄이 장면의 수명에 기대지 않게 해야 한다. 자신에게 '다시 열기'(`rapp`)를 보내는 것으로는 안 된다(다른 창이 보이면 창이 생기지 않고, 앱이 활성화된다).

### 파일 트리 클릭
- 더블탭+싱글탭 제스처 조합은 싱글 클릭 반응이 더블클릭 판정 대기(0.5 s) 뒤에야 오고, 파일은 더블클릭해야만 열렸다. 한 번 클릭(또는 방향키 선택)으로 바로 여는 방식으로 바꿨다.
- SwiftUI `List` + `OutlineGroup` 은 모델이 무엇을 발행하든 수천 행을 다시 구성·비교한다: 항목 5,300개 폴더에서 탭 전환 1.6~3.4 s, 하단 패널 토글 1.5 s(실사용 하네스 2026-11-24). `NSOutlineView`(`Panels/FileOutlineView.swift`)로 바꾸고, 폴더는 한 단계씩 백그라운드에서 읽고(하위 폴더는 펼칠 때), 본 폴더마다 아웃라인 뷰를 기억해 탭으로 돌아오면 다시 끼우기만 한다 — 60~90 ms.
- 문서 전환의 발행이 SwiftUI 에 반영되기 전에 `List` 의 데이터를 바꾸면(목록 다시 읽기) 표가 자기 대리자 호출 안에서 다시 읽혀 "reentrant operation in its NSTableView delegate" 경고가 난다. 목록 갱신은 뷰 갱신 밖(다음 턴)에서 한다.
- 펼침 화살표는 `NSButton` 이고, macOS 27 의 버튼은 `mouseDown` 에서 중첩 추적 루프를 돌지 않고 바로 돌아와 `mouseUp` 때 동작한다. 그 사이에 앱의 이벤트 큐에서 다른 `leftMouseUp` 이 나가면 누름이 거기서 끝나고, 뒤이은 진짜 `mouseUp` 은 버튼이 아니라 목록으로 가 그 클릭만 무시된다(바로 앞에 행 클릭이나 펼침·접힘이 있었을 때: 12번 중 11번; 앞에 아무것도 없으면 15번 모두 정상). **미해결**: 실사용 하네스의 전체 묶음에서 폴더 화살표의 첫 클릭이 간헐적으로 무시된다 — 위의 순서가 정확히 그 모양이지만 전체 묶음에서 무엇이 그 상태를 만드는지는 재현하지 못했다(기각: 행 이름을 누른 뒤의 간격, 연달아 누르기, 기계 부하, 앞 시나리오가 큐에 남긴 이벤트). 사람의 마우스 하나로는 만들 수 없는 순서다. 다시 나오면 하네스가 누르는 동안 큐를 떠난 마우스 이벤트를 적어 둔 것(`RealUseContext.lastArrowPress`)으로 가른다 — 기다림을 넣어 가리지 않는다. 합성 클릭을 보내기 전에 앱이 이미 활성이면(사용자가 그 창이나 Dock 아이콘을 눌렀거나 앞 걸음이 활성화했다) 물러나고 계속하되 문제(`focus`)로 남긴다 — 어느 쪽이든 하네스가 사용자의 포커스를 쥔 채 돌았다는 뜻이다.

### 자동화 실행 (셀프테스트·하네스)
- **"자동화 실행"의 뜻은 둘이다**(`Apps/mac/AutomationRun.swift`). `isScripted` — 스크립트가 모는 실행: `--selftest`·`--selftest-open`·`--bench`·`--realuse`·`--snapshot`, 실행 시간 계측의 `--quit-after-launch`·`--bench-launch-log`. 앞에 앉은 사람이 없다 → 뒤에서 돌고, 시작 잠금을 걸지 않고, 종료할 때 묻지 않고, 전역 단축키를 시스템에 등록하지 않고, 밖에서 온 파일은 자기 픽스처만 연다(아래 항목들). `isIsolated` = `isScripted` 또는 `--ephemeral` — 사용자의 것과 떨어져 도는 실행: 설정·기본 문서 폴더·스냅샷·북마크·스니펫·매크로·사용자 문법·저장된 창 상태·창 프레임 저장값을 읽지도 쓰지도 않는다. `--ephemeral` 만 준 실행은 사람이 쓰는 실행이라 그 밖에는 보통 실행과 같다(창이 앞으로 오고, 시작 잠금 설정을 따르고, 밖에서 온 파일을 가리지 않는다). 전에는 이 판정이 일곱 군데에 실행 인자 목록이 조금씩 다르게 흩어져 있었다 — `--bench`·`--realuse` 를 `--ephemeral` 없이 주면 설정은 휘발성인데 북마크·스니펫·매크로·문법은 사용자의 실제 폴더를 썼다.
- 터미널·IDE 가 앞에 있을 때 앱을 띄우면 macOS 가 새 앱을 **활성화**한다. 셀프테스트가 5~8분 동안 앞에서 돌며 키 입력을 받았다(2026-11-24: 10번 중 9번). 스크립트가 모는 실행은 모두 활성화될 때마다 물러난다: `applicationDidBecomeActive` → `AppDelegate.stepBackIfAutomated` 가 `NSApp.deactivate()` 하고 창을 맨 뒤로 보낸다(`automationStaysInBackground` — 앞에서 돌라는 `--selftest-foreground`·`--bench-foreground`·`--snapshot-activate` 만 예외). 시작할 때만의 일이 아니다: 도는 중에도 Launch Services 가 같은 번들 ID 의 이 인스턴스를 앞으로 가져올 수 있다(Finder 에서 연 파일이 이리 올 때, 스크립트가 몇 분 뒤 두 번째 실행을 띄울 때). 실사용 하네스는 전에는 시작 1.2 s 뒤 한 번만 물러났다 — 이제 같은 처리기를 쓴다. 물러난 뒤에는 활성이었는지 알 수 없으므로 횟수를 세어(`stepBacks`) 로그에 적는다(하네스의 `launch: activated N times…`·`end: activated…`, 셀프테스트의 `isolation:` 줄).
- `.nonactivatingPanel` 을 `makeKeyAndOrderFront` 하면 앱이 비활성이어도 키 입력이 그 패널로 간다(Quick Append 의 설계). 뒤에서 도는 자동화 실행 — 셀프테스트만이 아니라 하네스·벤치·스크린샷(`automationStaysInBackground`) — 의 패널은 떠 있는 수준이 아니라 맨 뒤에 보이기만 하고 키가 되지 않으며, 검사는 텍스트 뷰에 직접 넣는다(떠 있는 키 패널은 사용자가 다른 앱에 치던 글자를 받아 간다 — 검사의 초안에 그 글자가 섞였다). 그래서 `--snapshot` 으로 찍는 `--quick-append` 패널도 뒤에·비활성 모양으로 찍힌다; 쓰는 중의 모양은 `--snapshot-activate`.
- 비활성 + 가려진 창은 2~3분 뒤 **App Nap** 에 걸려 타이머가 늦게 깨고 CPU 우선순위가 깎인다 — 시간을 재는 검사가 몇 배 느려지고 순서를 바꾸면 느려지는 검사도 바뀐다. 실행 내내 `ProcessInfo.beginActivity(.userInitiatedAllowingIdleSystemSleep, .latencyCritical)` 로 막는다.
- 창의 기본 높이는 화면의 쓸 수 있는 높이를 따른다(외장 모니터 1128 pt, 내장 화면 972 pt). 잠자기 뒤 창이 다른 화면에 뜨자 같은 코드의 시나리오 세 개가 실패했다 — 하네스는 창을 1280 × 972 로 고정하고(`--window-height`, `scripts/realuse.sh --height`), 시나리오는 창 높이에 기대지 않는다(보이는 문단은 그 시점에 다시 잡는다).
- 수정끼리의 간섭은 각자의 브랜치에서는 보이지 않는다. 영역별로 따로 고친 것을 합친 뒤에는 **전체 시나리오를 같은 창 크기에서 다시** 돌리고, 한쪽 빌드에서만 0건인 시나리오는 두 빌드의 차이(상대 장치)를 하나씩 꺼 가며 가른다. 이번에 '테마 전환 때 내용이 17~30 pt 움직인다'의 상대는 스크롤 장치들이 아니라 탭의 보기 위치 저장이 부르는 점 질의였다.
- **벤치도 뒤에서 돈다**(`AppDelegate.benchStaysInBackground` — `--bench`, 그리고 `scripts/bench.sh` 가 여섯 번 띄우는 실행 시간 계측; `--bench-foreground` / `scripts/bench.sh --foreground` 가 예전처럼 앞에서). 벤치는 키 창·첫 응답자·이벤트에 기대지 않지만(모델과 텍스트 뷰를 직접 부른다) 창이 완전히 가려지면 그리기가 빠진다 — 그래서 어떻게 돌았는지를 결과에 적는다(`Bench.RunMode` → JSON 의 `mode`, 표의 `Run:` 줄: 뒤/앞, 도중에 활성화된 적이 있는가, 시작·끝에 창이 가려져 있었는가). **뒤에서 잰 값은 뒤에서 잰 기준선과만 견준다** — `mode` 가 없는 옛 결과 파일(`docs/bench/baseline-0.6.0.json` 포함)은 앞에서 잰 것이다.
- **저장된 창 상태는 번들 ID 공용이다.** 테스트 빌드는 설치된 앱과 번들 ID 가 같아 macOS 의 '저장된 창 상태' 폴더를 같이 쓴다. 자동화 실행이 거기에 자기 창을 적으면(실측: 시작 30초쯤 뒤 `windows.plist`·`window_N.data`·`data.data`) 사용자 앱의 상태를 덮어쓰고, 그 실행이 강제 종료되면 남은 상태를 다음에 뜨는 인스턴스가 — 사용자의 앱도 — 복원한다. 떨어져 도는 실행(`AutomationRun.isIsolated`)은 `ApplePersistenceIgnoreState` 를 등록하고 창을 복원 대상에서 뺀다(`.restorationBehavior(.disabled)`) — 시작할 때 저장된 상태를 읽지 않고 실행 중에도 적지 않는다(같은 세 시나리오로 재서, 전에는 시작 때 `restorecount.plist`·30초 뒤 파일 셋이 쓰였고 뒤에는 그 폴더가 전혀 건드려지지 않는다). 등록 도메인은 우선순위가 가장 낮아 같은 키가 이미 저장돼 있으면 지므로, 실행 스크립트(`realuse.sh`·`bench.sh`)는 `-ApplePersistenceIgnoreState YES` 를 인자로도 넘긴다(먹었는지는 하네스 로그의 `launch: saved window state ignored=` 줄). 보통의 실행은 그대로다.
- **창 프레임 저장값도 번들 ID 공용이고, 위의 둘로는 막히지 않는다.** 창의 위치·크기는 휘발성 저장소가 아니라 표준 UserDefaults 에 `NSWindow Frame <이름>` 으로 적힌다. SwiftUI 는 `WindowGroup` 의 창에 자동 저장 이름을 걸지 않고, 창이 키 창이 될 때 자기 이름으로 직접 저장한다(`AppKitWindowController.windowDidBecomeKey` → `saveFrame(usingName:)`) — 뒤에서 도는 셀프테스트의 창도 시트가 떠 있는 동안 키 창이 되어, 설치된 앱의 저장값이 테스트 창의 1280 × 820 으로 바뀌었다. `.restorationBehavior(.disabled)` 와 `ApplePersistenceIgnoreState` 는 '저장된 창 상태'만 막는다. 끄는 공개된 방법이 없어, 떨어져 도는 실행에서만 창이 만들어지기 전에 `NSWindow` 의 저장·읽기·자동 저장 이름 걸기 구현을 갈아 끼운다(`AutomationRun.keepWindowFramesOutOfDefaults`): SwiftUI 의 재정의는 super 를 부르므로 거기서 막히고, 설정 창(자동 저장 이름으로 저장한다)과 빠른 추가 패널도 같은 메서드를 거친다.
- **전역 단축키는 기계 전체의 것이다.** 테스트 인스턴스가 빠른 추가 단축키를 등록하면 사용자가 누른 ⌃⌥N 이 그 인스턴스의 패널을 띄우고 메모가 임시 문서에 붙을 수 있다 — 설치된 앱이 떠 있어도 같은 조합의 등록은 오류 없이 성공한다. 스크립트가 모는 실행은 Carbon 에 등록하지 않고 장부만 적는다(`GlobalHotKey.registersWithSystem`): 컨트롤러의 상태와 설정 화면의 문구는 같고, 눌림은 `GlobalHotKey.press` 로 같은 길을 태우며, `takenElsewhere` 로 "다른 앱이 쓰는 조합"의 거절 경로를 시험한다.
- **스크립트가 모는 실행은 자기 픽스처만 연다**(`ExternalOpen.mayOpen`). 번들 ID 가 같아, 도는 중에 사용자가 Finder 에서 연 파일이 테스트 인스턴스로 올 수 있다 — 그러면 사용자의 파일이 숨은 창의 활성 탭이 되고 테스트의 다음 편집(입력·매크로·모두 바꾸기)이 그 파일에 자동 저장된다. 자기 것은 둘뿐이다: 시스템 임시 폴더 **바로 아래의, 이름이 `hyperedit-` 로 시작하는 폴더** 안(깊이 무관 — 임시 폴더 전체가 아니다: 다른 앱도 거기에 사본을 두고 외부 편집기로 넘긴다), 그리고 `--file` 로 준 시작 문서와 같은 폴더의 **직속 파일**(하위 폴더까지 받으면 `--file ~/Desktop/copy.md` 로 띄운 실행이 데스크탑 아래 전부를 연다. `TMPDIR` 을 바꾼 셸에서는 스크립트가 만든 폴더가 시스템 임시 폴더 밖이라 이 규칙이 있어야 한다 — Foundation 은 `TMPDIR` 을 따르지 않는다). 경로는 심볼릭 링크를 풀고 견준다(`/var/…` = `/private/var/…`). 그 밖은 열지 않고 출력 패널과 stderr 에 `[automation] not opened — outside this run's folders: <경로>` 를 적으며, `scripts/realuse.sh` 가 그 줄들을 보고서 뒤에 다시 보여 준다(끝난 뒤 다시 열라고). 그런 이름의 폴더 **안**이어야 한다 — 임시 폴더 바로 아래의 낱개 파일은 이름이 `hyperedit-…` 여도 픽스처가 아니다. 그래서 테스트 픽스처는 `hyperedit-` 로 시작하는 이름의 폴더에 둔다. `--ephemeral` 만 준 실행은 가리지 않는다.
- **하네스·셀프테스트·벤치는 프로세스당 한 번만 돈다**(`RealUse.run`·`SelfTest.run`·`Bench.run` 의 `started`). `ContentView` 가 `.task` 로 부르므로 창이 하나 더 생기면 그 창이 자동화를 또 시작하고, 열기 요청을 보내는 시나리오라면 그것이 창을 더 만드는 연쇄가 된다. 둘째 창은 생기면 안 되지만(위 '창 복구'), 생기더라도 자동화를 다시 시작하지는 않는다.
- **밖에서 연 파일의 시험.** 실제 Finder·`open` 은 쓰지 않는다(앱을 활성화하고, 설치된 HyperEdit 으로 갈 수 있다). 켜져 있을 때의 길은 delegate 의 `application(_:open:)` 을 직접 부른다(`open-external`). **자기 프로세스에 애플 이벤트('문서 열기' odoc·'다시 열기' rapp)를 보내지 않는다** — AppKit 의 처리기가 앱을 활성화할 때가 있고(세 번 중 두 번), 그 뒤에는 `NSApp.deactivate()` 로도 물러나지 않았다. 애플 이벤트를 풀어 delegate 를 부르는 것은 AppKit 의 일이라 손으로 확인한다. 꺼져 있다가 뜨는 길은 `scripts/realuse.sh` 가 맡는다: 전체 실행이거나 `--only` 에 `open-launch` 가 있으면, 임시 폴더에 만든 넷(텍스트 파일 둘 — 하나는 한글 이름 —, 폴더, 없는 파일)을 `--quit` 바로 뒤의 맨 인자로 준 짧은 두 번째 실행을 띄우고(상한 120 s) 그 결과를 `<out>/open-launch/` 에 둔다. 값 없는 옵션 바로 뒤에 두는 것은 일부러다 — AppKit 은 그 자리의 첫 파일을 옵션의 값으로 삼켜 넘기지 않는다. 무엇을 주었는지는 환경 변수 `REALUSE_LAUNCH_FILES` 로 시나리오에 알려, 기대하는 탭을 앱의 인자 해석과 따로 정한다. 손으로는 `scripts/realuse.sh --only open-launch`, 시작 잠금과 함께 보려면 `scripts/realuse.sh --only open-launch -- --locked`. 다른 시나리오의 실행에는 맨 인자를 주지 않는다(시작할 때의 탭이 달라진다) — 그런 실행에서 `open-launch` 는 옵션의 값이 탭이나 빈 파일이 되지 않았는지만 본다. 열기 요청 뒤에는 걸음마다 문서 창이 하나인지 세고, 더 생겼으면 닫고 그만둔다.
- **격리 검사.** 셀프테스트의 `isolation:` 줄들(`SelfTest+Isolation.swift` — 맨 끝에 돈다)과 하네스의 `automation-isolated`(`RealUse+Isolation.swift` — 목록의 맨 끝)가 같은 검사(`IsolationProbe`)를 쓴다: 창 프레임(이름으로 저장한 프레임이 설정에 닿지 않는가, 창이 자동 저장 이름을 받지 않는가, 저장값을 읽지 않는가, SwiftUI 가 키 창이 될 때 하는 저장이 거절되는가, 시작한 뒤로 이 실행의 창 프레임과 같은 저장값이 생기지 않았는가), 포커스(활성 앱이 아닌가, 활성화 처리기가 물러나는가, 빠른 추가 패널이 다른 창 위에 뜨지도 키가 되지도 않는가), 전역 단축키(시스템 등록 0·장부 1, `press` 로 패널이 뜨고 닫히는가). 지킴이가 빠진 빌드에서는 저장을 시도하지 않는다 — 깨진 빌드가 돌린 사람의 설정에 쓰지 않게.
- **하네스 스크립트는 자기가 띄운 앱을 남기지 않는다.** 앱은 비대화형 셸의 백그라운드 작업이라 SIGINT 를 무시한 채 뜬다 — Ctrl-C 로는 스크립트만 죽고 테스트 인스턴스는 시작 파일이 지워진 채 뒤에서 계속 돌았다. `scripts/realuse.sh` 는 INT·TERM·HUP 을 종료로 바꾸고 EXIT 트랩에서 자기가 띄운 PID 만 정리한다(신호 뒤 0.2 s 안에 사라진다). 로그의 `launch: language=` 줄은 `-AppleLanguages` 같은 인자가 정말 먹었는지 보여 준다.
- **합성 휠 이벤트의 수정키는 비운다.** 하네스는 휠 이벤트를 소스 없는 `CGEvent` 로 만드는데, 그런 이벤트의 flags 는 만드는 순간의 수정키 상태다 — 사용자가 다른 앱에서 ⇧ 를 누르고 있을 때 만든 **줄** 휠은 AppKit 이 가로 스크롤로 바꿔(⇧ + 휠) 세로로는 한 칸도 가지 않는다(flags 에 ⇧ 를 직접 넣은 줄 휠 한 칸: deltaX −1·deltaY 0·이동 0 pt. 픽셀 휠과 ⌥·⌃·⌘ 는 그대로 간다). `scroll-line-wheel` 이 가끔 한 칸이나 잇달아 몇 칸 0 pt 였던 것과 모양이 맞는다: 편집기 버전과 무관하고(v0.10.7 의 편집기 코드로도), 창이 가려졌든 아니든, 줄 휠만, 아무도 타이핑하지 않은 44번의 실행에서는 0번. 다만 직접 증명하지는 못했다 — 실행 중에 사용자가 ⇧ 를 누르고 있어야 확인된다. 이벤트를 만들 때 flags 를 비우고, 그래도 안 움직인 칸이 나오면 시나리오가 그때 눌려 있던 수정키·live scroll 알림 수·2초 안의 늦은 반영·창이 가려졌는지를 적는다.
- **출력 패널은 500줄에서 앞을 버린다**(`AppModel.log`). "요청 전에 센 줄 수만큼 건너뛴 뒤가 새 줄"이라는 식의 검사는 패널이 가득 찬 뒤(전체 묶음의 뒤쪽)에는 첫 새 줄까지 건너뛴다 — 새 줄은 줄 수가 아니라 시각으로 가른다(`open-external`).
- **하네스가 못 본 비용 회귀가 셀프테스트의 `perf` 줄에서 드러났다.** 입력 뒤 한 줄 밀기의 대체 경로(캐럿 줄을 재려고 뷰포트를 배치)가 문서 전체를 바꾸는 편집 뒤에 문서를 처음부터 훑어 — 배치 한 번 430~520 ms — 1.3 MB 전체 주석 토글이 150 ms → 1.4 s 가 됐는데, 스크롤·입력 시나리오는 그것을 잡지 못했다. 셀프테스트의 `perf toggle comment 1.3 MB`(280 ms → 4.1 s)·`perf format JSON 1.3 MB`(160 ms → 3.1 s) 줄이 그것을 보였다. 입력 경로(`insertText`·`scrollRangeToVisible`·편집 뒤 배치)를 건드리면 셀프테스트의 `perf …` 줄(typing·toggle comment·format JSON·macro ×100)을 전/후로 견준다.
- `gh pr merge --delete-branch` 는 그 브랜치를 체크아웃한 **git 워크트리를 통째로 지운다.** 머지 전에 워크트리를 `git checkout --detach` 해 둔다.

### 서명·공증
- 공증 통과 조건: hardened runtime, timestamp 서명, 그리고 **Release 구성에 `CODE_SIGN_INJECT_BASE_ENTITLEMENTS = NO`**. 이것이 없으면 `get-task-allow` 엔타이틀먼트가 주입되어 공증이 거절된다(실제 거절 사례). `scripts/make-dmg.sh`는 서명 뒤 엔타이틀먼트를 검사해 남아 있으면 실패시킨다.
- `scripts/make-dmg.sh`의 서명 모드는 자동 판별: 키체인에 Developer ID Application 인증서가 있으면 developer-id, Apple Development만 있으면 dev, 없으면 ad-hoc. 공증 자격 증명(App Store Connect API 키 또는 `notarytool` 키체인 프로필)이 있을 때만 앱(zip)과 DMG를 공증하고 스테이플한다.
- CI 시크릿은 인증서 `.p12`(base64)와 비밀번호, API 키 `.p8`(base64)·키 ID·발급자 ID, Homebrew tap 쓰기용 deploy key. `main`의 릴리스 워크플로는 서명·공증 시크릿이 없으면 첫 단계에서 실패한다(포크는 저장소 변수 `ALLOW_UNSIGNED_RELEASE=true`로 서명 없는 릴리스를 허용). `scripts/setup-signing.sh ci-secrets <cert.p12> <AuthKey.p8> <KEY_ID> <ISSUER_ID> [owner/repo]`가 .p12 암호를 프롬프트로 받아 `gh secret set`으로 시크릿 5개를 바로 등록한다(값이 화면·셸 기록에 남지 않음). 키 파일 패턴(`*.p8`, `*.p12`, `AuthKey_*`)은 `.gitignore`와 `scripts/check-sensitive.sh`가 막는다.

### 릴리스 빌드 환경
- **아키텍처는 명령줄에서 못박는다.** 프로젝트는 러너에서 그때그때 XcodeGen 최신판(`brew install xcodegen`)으로 만들어진다. XcodeGen 2.47 부터 만들어지는 스킴의 기본값이 "Match Run Destination" 이라, 목적지가 이 Mac(`platform=macOS`)이면 그 Mac 의 아키텍처만 빌드한다 — 러너에서 arm64 만 나와 `scripts/make-dmg.sh` 의 유니버설 검사가 0.11.0 릴리스를 멈춰 세웠다(2.46 까지는 타깃 설정대로 둘 다 나왔다). 릴리스 빌드는 `-destination 'generic/platform=macOS'` 와 `ONLY_ACTIVE_ARCH=NO ARCHS="arm64 x86_64"` 를 준다. 도구가 최신판으로 따라 올라가는 파이프라인에서는 도구의 기본값에 기대는 설정을 명시해 둔다.
- **CI 와 릴리스는 러너의 기본 Xcode 로 빌드한다 — 로컬 Xcode 보다 낮을 수 있다.** 로컬 SDK 에만 선언된 것을 `override` 하면 러너에서 컴파일되지 않는다: NSTextView 의 `textViewportLayoutControllerDidLayout(_:)` 는 macOS 27 SDK 부터 선언돼 있어, 그 앞의 SDK 로는 "method does not override any method from its superclass" 다. 그런 자리는 재정의 대신 런타임에 구현을 얹는다(`HyperTextView.noWrapViewportHook` — NSTextView 의 구현을 부른 뒤 제 일을 한다; 두 SDK 에서 같은 코드가 돈다).
- **큰 변경을 여러 PR 로 나눠 올릴 때**: (1) 먼저 전체를 드래프트 PR 하나로 올려 러너에서 한 번 컴파일해 본다(로컬 빌드가 못 잡는 SDK 차이가 첫 PR 이 아니라 가운데 PR 에서 드러난다). (2) 단위를 가른 **중간 트리마다** 빌드·셀프테스트·관련 시나리오를 돌린다 — 테스트 코드끼리의 의존(트랙패드 시나리오가 스크롤바 손잡이 도우미를 쓴다)과 "다른 단위의 수정이 있어야 통과하는 검사"(편집이 화면을 옮기지 않게 된 뒤로는 문서 전환 수정이 있어야 셀프테스트의 JSON 정리 검사가 통과한다)는 최종 트리에서는 보이지 않는다. 그런 단위는 하나의 PR 로 합친다.

### semantic-release
- `@semantic-release/exec` 명령 문자열은 lodash 템플릿으로 먼저 해석된다. `${VAR:-x}` 같은 중괄호 셸 문법을 쓰면 템플릿과 충돌해 릴리스가 실패한다(실제 사고). 셸 로직은 스크립트 파일(`scripts/set-version.sh`, `scripts/update-cask.sh`)로 빼고 exec에는 인자만 넘긴다.
- semantic-release는 태그가 없으면 1.0.0부터 시작하므로 0.x를 유지하려고 첫 태그 `v0.1.0`은 수동으로 만들었다. `release-tag.yml`은 수동 태그에 DMG·릴리스를 만드는 보조 워크플로이며, 이미 릴리스가 있으면 건너뛴다(멱등).

## 6. 저장소 운영

- **브랜치**: `main`이 릴리스 브랜치. 기능은 브랜치 → PR → squash merge.
- **커밋 규약**: Conventional Commits. `feat` → 마이너, `fix`/`perf` → 패치, `feat!`/`BREAKING CHANGE` → 메이저, `docs`/`chore`/`refactor`/`test`/`ci`/`style`/`build` → 릴리스 없음, `(themes)` 스코프 → 패치. 제목은 한국어도 허용(commitlint `subject-case` 해제, 헤더 100자). 로컬 훅 `scripts/install-hooks.sh`, PR에서는 commitlint 액션.
- **CI (`ci.yml`)**: 테마 생성·drift 검사·스키마 검증(ubuntu) · 민감 정보 검사 `scripts/check-sensitive.sh`(비밀 파일 확장자, 키·토큰 패턴, 홈 디렉터리 경로, 이메일) · commitlint(PR 커밋 전부, 저장소 devDependency를 `npm ci --ignore-scripts`로 설치해 실행) · `swift test` + XcodeGen + 서명 없는 `xcodebuild`(macOS). 모든 액션은 커밋 SHA로 고정하고 `persist-credentials: false`로 체크아웃한다.
- **릴리스 (`release.yml`, macOS 러너)**: `main` push → 서명·공증 시크릿 확인(없으면 실패, 저장소 변수 `ALLOW_UNSIGNED_RELEASE=true`로만 우회) → `npm ci --ignore-scripts`(락파일 고정) → 임시 키체인에 인증서 가져오기 → semantic-release가 버전 계산 → `CHANGELOG.md`·`VERSION`·`Config/Version.xcconfig` 갱신 → 테마 생성 → `scripts/make-dmg.sh`(서명·공증) → `scripts/update-cask.sh`로 `Casks/hyperedit.rb` 생성 → `chore(release): x.y.z [skip ci]` 커밋 + `vx.y.z` 태그 → GitHub Release(DMG·`SHA256SUMS`·`hyperedit-themes.json`, 영·한 설치 안내) → **별도 단계**에서 버전이 바뀐 경우에만 `HOMEBREW_TAP_DEPLOY_KEY`로 tap 저장소에 cask 푸시(키는 이 단계에만 노출) → 임시 키체인·키 파일 정리. 빌드 번호(`CURRENT_PROJECT_VERSION`)는 `github.run_number`.
- **설치 채널**: Homebrew `brew tap Hyeongcheol-An/tap && brew trust Hyeongcheol-An/tap && brew install --cask hyperedit`, 또는 DMG. Homebrew 7(2026-09)부터 외부 tap 의 cask 는 `brew trust` 로 한 번 신뢰 처리하기 전까지 `Refusing to load cask … from untrusted tap` 으로 거부되므로(2026-11-05 새 Mac 첫 설치에서 확인) README·가이드 11종·릴리스 노트 템플릿의 설치 안내는 그 줄을 코드 블록 안의 단계로 둔다. cask의 `zap`은 Application Support·Caches·Preferences·Saved State를 정리한다.
