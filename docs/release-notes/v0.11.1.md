## Release notes

Word wrap off no longer freezes large documents, and the editor now scrolls sideways properly.

### Fixed

- **Freezes with word wrap off** — turning word wrap off in a 1.3 MB note blocked the app for 1.7–3.4 s, and with wrap off every change of theme, syntax colors or text size froze it again for 1.7–4.4 s. A 4 MB log opened with wrap off took 15 s, and one wheel step in it 13–17 s. None of these stalls is left: the log opens in 0.35 s and scrolls at 3.7 ms a step. Typing with wrap off now costs the same as with wrap on (on a file of long paragraphs it was 17.0 ms a key against 13.9 with wrap on; now 14.4 against 14.5).
- **Sideways scrolling** — with word wrap off the editor often did not scroll sideways at all. In a 3,000-line file whose longest line was 17,334 pt wide the text stayed as wide as the window: no horizontal scroll bar, ⌘→ did not follow the caret to the end of the line, and on a long line far down it threw the view to the top of the document. In other files the width was unrelated to the text (1,644 pt for a note whose longest line is 867 pt). The scroll range now reaches the widest line shown so far and grows when a longer line comes on screen.
- **Following the caret sideways** — line ends (⌘← / ⌘→), typing and Hangul composition past the right edge, and find results far to the right now bring the caret into view. Moving left one character at a time no longer leaves the caret hidden for one keypress at the left edge.
- **Column blocks** — dragging a column block across a line shorter than the block threw a sideways-scrolled view back to that line's end (from x 600 to x 169), so the block grew to the wrong columns (52–90 instead of 90–102).
- **Text size and reloads** — changing the text size while looking at the end of a long line keeps the same characters in view, in both editors of a split, and a file that another program keeps appending to no longer returns to the first column each time it is read again.

### Known limitations

- The horizontal scroll range covers the widest line shown so far, not the widest line of the document: a longer line further down widens it when it scrolls into view. It does not shrink until you switch to another file or toggle word wrap.
- Coming back to a tab starts at the first column; the sideways position is not kept per file.

### For contributors

- `Editor/HyperTextView+NoWrap.swift`. When the text container does not track the view's width, every read of `-[NSTextView textContainerOrigin]` lays out the whole document — 22–26 ms a call in a laid-out 1.3 MB file, 2.1–2.4 s after anything that invalidates all layout — and viewport layout, frame changes, the insertion point and our own caret geometry read it on every step. Its value is always the container inset, so the getter returns the inset directly while wrap is off (checked against AppKit's value in left-to-right and right-to-left documents and under an Arabic interface: no mismatch).
- AppKit's horizontal auto-sizing is unreliable under TextKit 2, so the view keeps its own width: the wider of the editor and the widest line laid out so far, measured on every viewport layout and before a range is scrolled into view. The text container stays infinitely wide — a finite width sends right-to-left paragraphs to its far edge. A font change rescales the measured width of every editor of the session once, from the primary editor; doing it per editor went wrong in a split in either order.
- Real-use scenarios `nowrap-hscroll`, `-caret`, `-draw`, `-rtl`, `-split`, `-layout`, `-typing` and `-log` (`RealUse+NoWrap.swift`). On the previous code the first set reports 43 functional issues and 1,268 stall rows; now none. The word-wrap toggles and the jump to a far line have time budgets, so the stalls cannot come back unnoticed. `scroll-log` takes 14 s and can go back into the full run.

### Compatibility

- macOS 15 (Sequoia) or later. The DMG (`HyperEdit-<version>-universal.dmg`) contains one universal binary that runs natively on Apple Silicon (arm64) and Intel (x86_64) Macs.
